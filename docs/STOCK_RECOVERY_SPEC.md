# 完整成本帳的備份與找回

此規格補充 [庫存規格](INVENTORY_COST_SPEC.md) 的備份及交付要求，並保留 [成本報表規格](STOCK_REPORTING_SPEC.md)、[售價試算規格](COST_PRICING_SPEC.md) 與原始 31 項 ERP 要求的全部門檻。基線來源為 `d4a3a34`：成本帳已含於原生匯出，但正式還原拒絕成本集合；瀏覽器集合尚未識別成本帳。目標是讓完整原帳可核對、可保護還原及按原編號找回，不能以丟棄新資料或關閉保護達標。

## K1 完整快照

每份成本帳備份同時包含全部業務集合、成本事件、成本回執、原配方依據與成本來源。零事件、缺少兩者之一、重複／缺號／錯序／改內容／錯雜湊／錯回執須可分辨；缺資料不能猜成空帳。原生與瀏覽器的完整集合對應與內容簽章必須包含新集合；雲端部分同步不得忽略本機或來源成本帳。

## K2 逐筆驗證

正式寫入前重播原始成本鏈與每筆回執，驗證期初快照、來源、數量保管、整數分成本及原業務操作。來源業務編號、品項、單位與不可變部分必須對得上；不能只驗成本鏈內部雜湊後接受與訂單分離的帳。排序依事件序號，不能拿匯出時的字典序當歷史順序。未知成本、已知零、原始金額與原配方保持原文，不重建過去 FIFO。

## K3 一起還原與回滾

只在真正管理員的已核對預覽後，於同一原子提交保存還原前保護副本、原編號索引、全部業務與成本集合、更新的執行期識別及復原回執。任何晚期失敗、損壞、空間不足或過期資料均保留原帳與原輸入。重送同編號回原回執，不再次刪寫或改動訂單、庫存、金流與會員。

## K4 執行期識別與相容保護

還原會更新執行期識別以拒絕舊裝置的新操作，但不得重寫成本事件原 epoch、時間、編號或雜湊。新識別與被還原成本鏈須有受保護的權威綁定。曾使用新成本帳的資料庫，即使還原成本啟用前的備份，舊版本寫入者仍須被擋；相容版本可正常營運或從原保護副本找回。空成本帳保留的相容性標記，透過新裝置匯入、初次移轉及重新開啟時也必須安裝永久柵欄；未知的未來標記須拒絕，不能降版覆寫。保護不得透過公開 IPC、任意 SQL 或一般寫入開關解除。

## K5 原編號找回

被還原移除的收銀、退貨、進貨、餐飲、損耗、新商品期初、成本開帳及補登等原編號保持不明狀態，不能再造一筆。找回原完整保護副本後，各業務與成本回執仍逐筆相同；原事件不補造、不重新計價、不重新收款。還原後已有新的營運資料、店面不符、內容變更、帳號偽造或回執損壞時，只提供可核對的下一步，不能自動覆蓋新資料。

升級加入的空成本集合不屬於新的營運資料，不能使舊版本已保存的保護副本失去可復原資格；有實際事件的成本集合仍參與完整異動比對。不得改寫舊副本簽章或原始內容以通過檢查。

## K6 瀏覽器與同店裝置

瀏覽器完整原子紀錄、備份、保護副本、原編號索引與版本柵欄識別成本集合；不認識此功能的寫入應明確拒絕並保留資料。實際 HTTPS 配對裝置繼續使用同一 SQLite 權威，不建立本地成本／付款副本。舊分頁、還原後執行期、不同角色及回覆遺失的核對須使用真正傳輸與認證。

## K7 少字與驗收

還原預覽先回答「找回哪一天、幾筆訂單、多少商品與成本紀錄」，保護副本與進階核對可展開。既有恢復操作、四語、兩種風格、360px 與大字模式保持可操作。資料遺失風險的確認必須具體，不能以一鍵跳過必要核對；真人與實體裝置驗收獨立保留。

## K8 證據門檻

先以真實原生資料庫證明目前拒絕成本還原且沒有丟資料，再用同樣業務歷史驗證完整備份／還原／找回、跨版本永久柵欄、超過 50 筆歷史、舊參考資料、原始角色、晚期回滾、回覆遺失與重新開啟。用真正 2.16.0 解出的舊程式做正負控制；新安裝檔與真正關閉的 2.16.0 副本升級仍須獨立證明。單一模型、行數、測試數與零 finding 不證明完整 ERP 或公共安全。

## 開發進度與待補證據

目前已實作當前完整成本帳的原生／瀏覽器匯入匯出、原生原子還原、保留原編號的同裝置復原，以及空成本帳跨裝置移轉後的舊版本寫入保護。還原預覽先顯示四種紀錄，其餘可點開。已使用隔離的原生資料、實際獨立瀏覽器與配對 HTTPS 介面驗證這些流程；不是新的安裝版交付。

保護副本的來源圖與原編號索引，目前仍保留在各裝置的復原資料中，尚未完整攜入外部 JSON 備份；換電腦不能假設同時找回所有已被還原移除的原交易。完整異機災難復原仍是必要工作，不以現有成本集合匯出替代。獨立瀏覽器的成本交易、原操作者跨裝置身分核對、新安裝檔、實體裝置與真人易用性驗收也仍開放。

# 掃桌碼到備餐工作單

狀態：開發中。延續原始 31 項 ERP、完整備份 B1–B8、庫存 I1–I12 與跨格式 X1–X7，不以這次餐飲流程取代整體完成條件。所有店家、全部功能免費；本階段使用隔離資料與既有開發分支，不啟動真實店面或公網通道。

## K1 桌號由店家桌碼帶入

老闆先確認正式出餐設定，填桌數即可產生逐桌 QR。桌碼由目前店面、登記桌號與簽章核對，顧客掃碼即看到桌號，不再手填。修改網址、換桌、已移除桌碼與別間店的桌碼不能變成可信桌號。桌碼是公開點餐入口，不是管理員身份；不得洩漏簽章密鑰、庫存成本、配方或帳號。

## K2 顧客送單可跨重開核對

顧客看到品項、數量、總額，確認後才送出；先保存原請求內容與編號。回覆遺失、重新整理、關頁重開都沿用原請求核對，不能再建立另一張單。未收到完整的訂單編號、金額與追蹤回覆，不能清除原請求。空間不足或損壞暫存保留資料並停止送出。已受理請求的重試先核對原內容，即使菜單、桌碼或庫存後來變動，也不能重送成新單。

## K3 一張顧客原單接進正式出餐

尚未接單的顧客請求不收款、不扣庫。店家按接單後，在同一原子交易將原單對應到唯一正式出餐單，按已確認的目前售價、原料配方與實際產能預留。使用原顧客單號、明細、金額與可信桌號，不能用另一張單、假價或重複接單覆蓋。預設帶入當前日期與時段，產能或價格有變更時保留原單並明確要求核對，不猜下一天或偷偷改價。

## K4 同一張工作單，付款與製作分開

正式出餐沿用既有「已預留 → 製作中 → 可取餐 → 已交付」與外送流程。顧客點餐入口與預訂出餐共用同一份進度；接受即進入備餐工作單，不必重新抄單。付款只經既有正式收款，完成交付前必須收款。製作前取消釋放預留；製作後取消保留耗用與損耗；已付款取消沿用正式退款。顧客只可用自己的追蹤憑證讀最少進度，不暴露其他桌、聯絡資料、款項內部資訊。

## K5 原編號、成本與版本保護

接單和後續操作先保存原編號，再交給目前身份的原生／瀏覽器／配對 HTTPS 權威處理。斷線、重啟、晚期失敗和同編號重送不重複預留、收款、扣庫或增加成本事件。新桌碼與接單關聯須保留於完整備份與原始保護副本，雙向格式搬移後仍可查原單。舊寫入者必須停止，不能拆開關聯、清除進度或忽略保護。

## K6 廚房與列印界線

接受的單自動顯示桌號、品項、數量與備註，供廚房開始製作與完成。列印須使用正式單據的權威內容，不能由畫面自行捏造收款或製作內容；列印指令送出與紙張實際成功分開呈現。自動列印、實體設備與長時間營業驗收仍是原始目標中的待辦，不能用電子工作單或模擬印表機宣稱已全面完成。

## K7 少字、跨裝置與四語

老闆只填桌數，顧客只選餐點與確認；店員從待處理單按「接單備餐」，接著使用同一張工作單。保持明亮／海報兩風格、四語與 360px；顯示明確桌號、未收款與下一步，細節收起。配對手機共用店面電腦資料，沒有離線庫存／付款副本；獨立瀏覽器可讀取及處理已搬入的顧客／出餐資料，沒有公網接單服務時不能假裝在接收新顧客。

## K8 驗證與未完成範圍

先凍結舊程式的桌號手填、材料菜單缺漏、接單未預留與重開遺失請求控制，再用相同原始資料重驗。須涵蓋正式 SQLite、獨立瀏覽器、實際 HTTP 菜單與顧客、認證 IPC、憑證釘選 HTTPS 店家、FileReader／重啟／完整備份、配方與成品、最後庫存／產能、改價、同編號改內容、角色／偽造來源／撤銷、晚期回滾及回覆遺失。正式六控制資安、實體設備、老人兒童真人、Uber Eats／foodpanda 與完整 ERP 仍分開驗收。

# POS Pro 本機安全與資料完整性檢查 — 2026-10-07

本次檢查修正已重現的安全與交易問題。所有使用者、店家規模與軟體功能維持免費。檢查範圍是這個專案的原始碼、正式前端建置、隔離的桌面／瀏覽器執行流程與本機 SQL 權限模擬；沒有修改使用者營業資料或正式 Supabase 專案。

## 已修正的問題

| 問題與影響 | 修正與驗證方式 |
|---|---|
| 儲存尚未完成就顯示收款成功；回覆中斷後重試可能重扣庫存 | 結帳等待持久化確認，先保存請求編號；使用原編號查詢與重試。實測提交後遺失回覆、重新載入與再次核對，交易只寫入一次。 |
| 退款、儲值與報廢的金額／庫存可部分寫入或信任畫面傳入值 | SQLite 在交易內重新計算；瀏覽器業務資料以單一原子記錄提交。儲值、退款有穩定請求編號；拒絕超退與同編號不同內容，保存失敗保留原資料。 |
| 更新版本標記可能覆蓋自訂管理員；共用預設密碼 | 保留現有帳號與憑證，空帳號庫才建立管理員。桌面端驗證密碼、角色、登入期限及帳號異動；已確認的舊弱密碼先驗證再要求升級。 |
| 畫面可冒充管理員、呼叫敏感 IPC | 主程序檢查目前主視窗／frame、來源與已驗證身分，敏感動作依持久化角色授權；sandbox、導覽、彈窗與權限入口也有限制。 |
| 顧客點餐可取得成本或其他人的訂單；偽造價格／數量 | 公開商品欄位白名單、伺服器定價、來源與格式驗證、限流、請求去重。個別訂單以私人 Bearer token 查詢，取消全體訂單廣播，外部 tunnel 預設關閉。 |
| Windows 列印把名稱插入 `cmd.exe` 指令；失敗仍可能回報標籤成功 | 改用固定程式呼叫 Windows RAW spooler API，名稱與檔案以資料傳遞；設定 child timeout、隱藏視窗、檢查回覆與清除自有暫存。測試惡意名稱、失敗回覆與真實 loopback TCP 傳輸。 |
| 菜單商品 ID 的引號可形成 HTML 屬性；CSP 下搜尋失效 | 完整跳脫文字與屬性，改用事件監聽器。實際載入菜單 DOM，驗證特殊 ID、加入／移除購物車與搜尋。Excel XML 匯出也修正屬性跳脫與字串型別。 |
| 歷史備份受畫面筆數限制；損毀匯入可能先清空資料 | 備份直接匯出完整資料庫；匯入與還原在交易內執行，保留舊備份未包含的集合。以超過畫面上限的歷史資料及注入失敗測試。 |
| 多次部分退款後全退的報表可能殘留負數；成本隨商品修改漂移 | 保留所有帶正負號的交易與退款，排除尚未收款的顧客訂單；保存成交成本。依累計退款比例取整後減去已退部分，避免累積誤差。 |
| 自動雲端拉取覆蓋本機新交易；雲端同步傳送本機帳號 | 取消自動替換；同步要求 Supabase Auth，帳號留在本機。拉取前備份、核對資料 revision，拒絕等待期間本機新增交易後的替換。 |
| 舊 Supabase policy 可能讓任何人讀寫；誤用管理金鑰 | SQL 為業務表套用身分隔離與 restrictive RLS，撤銷匿名權限；拒絕 service role／secret key。以 PGlite 執行合法本人、第二身分、匿名、偽造 owner 與舊寬鬆 policy 控制。 |
| 離線前端只快取入口，遺漏建置後 JS／CSS；另一分頁覆寫資料 | 建置時產生完整且有版本的離線快取；原子寫入與單一編輯分頁鎖。正式 HTTP 前端斷網後重新載入並收款，第二個編輯分頁被拒絕。 |
| 舊直接與間接依賴含已公告弱點 | 更新解析後的依賴與 native SQLite，確認實際 Electron 啟動。npm advisory 項目由 44（4 critical、28 high、9 moderate、3 low）降至 0；沒有使用強制降版。 |

列印 API 的流程依 [Microsoft RAW 列印文件](https://learn.microsoft.com/en-us/windows/win32/printdocs/sending-data-directly-to-a-printer) 實作。Windows 佇列接受資料與 TCP 寫入完成，仍需實體印表機確認紙張、編碼、切紙與錢箱動作。

## 驗證範圍與重現

需要 Node.js 24 以上；安裝後由 electron-builder 重建 native SQLite。

```powershell
npm ci
npm audit
npm test
npm run test:native
npm run test:desktop
npm run test:offline
```

測試使用隔離資料庫與自有暫存目錄。桌面驗證使用正式建置、正式 preload 與共用正式 IPC handler；瀏覽器驗證使用正式 HTTP 前端與 Service Worker。測試程式檢查 child exit 和明確成功標記，不以父 shell 成功或畫面按鈕存在作為通過依據。

本次結果為 308 個 Vitest 測試、12 個真實 SQLite 測試、5 個桌面 UI 測試與 3 個離線瀏覽器測試，共 328 個通過。原先的 214 個測試也包含在這次完整回歸中。另驗證點餐服務連接埠占用時不會誤報啟動成功，以及 Windows 真實 spooler 拒絕不存在的印表機。

| 六項控制 | 實際證據 |
|---|---|
| scope | 固定本機來源、隔離資料、角色、資產與邊界；正式雲端、真實硬體與簽章發行另列缺口。 |
| coverage | 合法收款、退款、儲值、備份、登入、顧客點餐配對錯誤輸入、未授權與中途失敗測試。 |
| provenance | 固定原始碼清單及 SHA-256、套件 lock、Node／Electron 身分、建置摘要與 child 結果。 |
| normalization | 分別記錄原始失敗、修復後拒絕與正常成功；不把未執行維度計入通過。 |
| admission | 主視窗與 frame、持久化角色、登入期限、HTTP origin、身分隔離及私人訂單 token 控制。 |
| adapter-integrity | 真實 UI → adapter → SQLite／原子瀏覽器記錄 → 確認 → 重開流程，測試重複、失聯與回滾。 |

專案原始碼檢查的 `audit.config.json` 只排除可重建依賴、建置與本機證據；依賴另由 npm 掃描，正式建置另有執行驗證。原本 R6 的四份交易 contract／coordinator 檔案保留，實際呼叫端接上這些控制。

## 尚未驗證或仍需改善

- **正式 Supabase：NOT_CHECKED。** 本機 SQL 模擬通過，不代表線上資料庫已部署這份規則。依 `SETUP_SUPABASE.md` 部署後，應以兩個實際帳號與匿名請求另外驗收。
- **多裝置雲端同步：REVIEW。** 本次防止同一裝置等待期間被覆蓋；目前手動 upsert 不提供跨裝置衝突合併與整批遠端交易。
- **實體印表機、相機、錢箱：NOT_CHECKED。** 邊界與傳輸已測，實機相容性仍需要硬體驗收。
- **簽章安裝程式與安全自動更新：NOT_CHECKED／REVIEW。** 本次沒有建立或簽署正式安裝程式；來源更新仍由維護者人工審查，沒有宣稱已具備安全自動更新。
- **JS／JSX 自動架構依賴圖：NOT_CHECKED。** Cleanup 的 Python AST 量尺不適用，不能用執行測試冒充完整架構量測。檔案長度檢查仍有 3 個 FAIL（`database.js`、`PurchasePage.jsx`、`SettingsPage.jsx`）與 2 個 REVIEW；本次保留原門檻，後續需拆分責任並重跑交易測試。
- **既有訂單成本：REVIEW。** 新交易有成交成本快照；舊資料沒有快照時，舊報表成本只能依現有商品資料估算。
- **本機瀏覽器帳號與資料：使用者控制裝置的信任範圍。** 裝置操作者可改寫本機儲存，不能把前端角色當成對裝置擁有者的安全隔離。
- **第三方服務與硬體費用。** 軟體全部免費；Supabase、LINE、網路、金流或硬體若由外部供應者收費，費用由該供應者決定。

零 dependency advisory 只表示該次資料源沒有回報已知套件弱點，不是零弱點保證，也不是企業級 POS 的功能／可靠性認證。

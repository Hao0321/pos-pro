# 訂位到點餐：共同保存規格

狀態：M18c 開發版本。私人連結、網址更新、訂位共同建立餐飲單、完整併桌票券、未收款接待及完整復原引導已接通；已有原生／瀏覽器交易測試及網站、原生與配對員工的實際畫面證據。新異動須通過整批回歸與來源發布核對；這不是完整 ERP、正式對外部署或實體裝置驗收。全部店家、全部功能免費，完整 ERP／CRM、會員福利與訂金目標維持原範圍。

## RD1 店員實際操作

客人報到、入座後按「開始點餐」，沿用訂位姓名、電話、實際桌號與店面當地時間。既有餐點選項與一般商品的接單表單都要可用，不另建簡化版餐點帳。會員可明確選取既有身分，不依同名或同電話自動合併，也不自動加入行銷名單。點數與券依後續實際活動及原交易帳本處理，不能憑訂位就發放。

確認餐點後，同一次保存建立正式餐飲單、原料預留與成本來源、廚房工作，以及訂位和餐飲單的永久連結。失去回覆後沿用原編號查回。保存成功後直接定位到該餐飲單，可備餐、收款、交付，再回到同一桌。追加餐點是明確的新接單操作；重複按鈕或兩個裝置競爭舊版本不應重複預留原料。

離席是實際桌位事件，交付與收款是餐飲事件，不因出餐就自動認定客人離席。未結餐飲單仍需清楚顯示，不得因釋放桌位就遺失未收款或耗用原料。

接待金額由既有餐飲原單與實收、退款歷史計算。缺少原單時顯示待找回，不能把未知金額當零。部分收款、退回收款及取消後，接待同步顯示實際剩餘；離席前提醒，客人確實離開時仍保留未收款與原餐點單。跨日期的未結餐點可以集中查找。

## RD2 原編號與來源

餐飲單沿用現有表單凍結的 child ID、時間與菜單核對資料。訂位父操作 ID 由 `reservationDiningOperationId(storeId, childId)` 穩定導出，父操作類型為 `dine`。父輸入含訂位 ID、核對時訂位版本、可選會員 ID、完整 child 請求與確認旗標。

Child 請求帶 `reservationDining` 來源：協議 `pos-reservation-dining/v1`、父 ID、訂位 ID／版本、實際桌 ID 與當時桌名、可選會員 ID。父和子都綁同一店面與還原世代。一般餐飲寫入入口不得自行宣稱此來源，只有訂位共同保存流程能建立；原子操作內仍須使用既有餐飲、庫存、成本及列印規則。

父回執保留可重播的連結及 child 原請求簽名；餐飲單保留同一來源與完整桌名，不以備註代替正式桌號。多桌名稱不得悄悄截斷；需要時用新版廚房票券，舊 v1 的意義保持不變。

## RD3 保存、回覆與復原

原生使用同一 SQLite transaction；獨立瀏覽器使用同一筆既有原子業務紀錄與既有鎖。任何晚期錯誤都回滾父、子、庫存、成本和列印工作。實際列印喚醒須在共同保存提交後才發生。

回覆必須驗證父原編號與簽名、child 簽名與實際餐飲單、當前訂位連結、店面／世代及啟用成本帳時的成本回執。只有這些都成立，才能清除待確認內容並跳到餐飲單。保存後斷線、重新開啟、重試與同 ID 改內容須有實際 native／paired／browser 證據。

完整備份須交叉核對父子及桌號來源。還原到接單前時，非回滾歷史會保留已知餐飲承諾並暫停接單；不能僅補訂位回執就當作餐飲單、原料與收款已找回。缺少整組資料時引導老闆用完整備份預覽與確認復原，不重配庫存或暗中改寫既有帳。

暫停涵蓋共用保存入口的一般餐飲、POS、庫存、儲值等新的業務異動；原單核對與老闆確認的完整復原保留。既有批次到期觀察不代表新接單。仍被已知餐飲承諾引用的會員不能從一般刪除入口移除；不把復原紀錄中的會員關聯當成不存在。原生共用店面使用同一個同步保存權威；獨立瀏覽器由既有鎖和單筆業務紀錄保護，不建立分岔的手機帳。

## RD4 必要驗證

實際免登入訂位 → 原生與配對到店／入座 → 菜單與一般品項 → 共同保存 → 桌號廚房單 → 原付款流程 → 交付與離席；不同會員明確選擇與權限、最後原料競爭、重複點擊、遺失回覆與重開、晚期回滾、跨儲存備份及真正前版16暖／冷啟動保護。四語、兩種風格及360px都需操作證據；實體手機、真實首次使用、對外部署與印表機仍分開驗收。

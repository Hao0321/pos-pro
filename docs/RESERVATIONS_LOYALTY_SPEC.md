# 訂位、候位與店家自訂會員福利

日期：2026-10-19。狀態：使用者新增的必要目標，尚未完成。全部店家、全部功能免費；本文件不代表已超越 inline 或 Ocard。

## RL1 一套日常流程

顧客用手機選日期、人數、時段，確認後取得可再次查看的訂位紀錄。店家從「今天的客人」確認到店、安排桌位、開啟點餐、結帳並累積福利；訂位、會員、餐飲訂單、POS 和 ERP 引用同一間店的永久身份與原單。現場客、電話預約和網路訂位使用相同容量規則。沒有參加會員也能訂位；加入會員與行銷同意分開。

首次設定用「營業時間 → 桌子與人數 → 分享訂位網址」三步完成。可用範本起步，進階條件收在展開選項中。老人、小孩首次使用的可用性必須實測，不能由開發者代操作推定；觸控目標至少 44×44 CSS px，手機、鍵盤、明亮及藍白視覺、繁中／簡中／英文／日文均需驗收。

## RL2 訂位容量與候位

店家設定桌位容量、可合併的桌子、餐期、用餐時間、清桌緩衝、休息日、例外營業日、最後受理時間，以及網路與現場可用容量。系統建議適合桌位，由店家保留調整權；時間區間使用半開區間，套用用餐與緩衝後檢查所有重疊，不可只按每小時人數加總。跨午夜仍歸正確營業日；儲存時區與時間實值，拒絕不存在或歧義的當地時間。

狀態至少包含待確認、已確認、已到店、入座、結束、取消與未到。候位是不同的排隊紀錄，不能當作已訂位。空桌釋出後可建議候補；轉為確認必須原子檢查容量與有效期限，兩台裝置只允許一位取得最後桌位。店家調整容量、移桌、延長用餐或併桌時，先呈現受影響訂位再確認。公開頁只公布可用時段，不公開客人的姓名、電話、會員等級或內部備註。

## RL3 訂金、提醒與變更

訂金條件依日期、餐期、人數及活動設定；結帳可抵實際已收訂金，取消與退款沿用原收款與政策版本。訂位成功、訂金已收與退款完成是三個不同事實。人工記錄銀行／現金不等於已代扣款。刷卡、綁卡、失約扣款、簡訊及 LINE 等外部通路逐項驗證供應商、費用與回執，未接通時保留手動替代流程。

提醒建立具穩定 ID 的待送工作；只有已授權通路才發送。逾時、取消或重送不重複通知，也不能因訊息失敗取消已成功的訂位。客人使用有期限、可撤銷的私密憑證查看／改期／取消自己的訂位；網址不含明文個資，改期需重新檢查容量。

## RL4 店家自己設計福利

店家可從「消費集點」「集滿換商品」「滿額折價券」「生日／入會禮」開始，設定後先顯示自然語言摘要與實際金額範例，再啟用。支援免費會員分級、自訂升等條件與福利、指定品項、活動日期、加倍點數、每人／每單上限、發行總量、到期時間、使用時段／門店／品項、最低消費與併用規則。活動版本只影響新發放；已發點數與券保留當時條件，不能被靜默改寫。

點數以帳本記錄取得、保留、使用、退回、到期與人工更正；每筆綁原交易和規則版本。以真正符合條件的消費金額計算，排除儲值本金、訂金重複入帳及退回部分。點數批次按明確順序使用，退款還原原批次及原期限；已過期的額度不可自動延長。舊系統點數／儲值搬入要獨立核對，不能把未知餘額當零，也不能將會員與應收客戶憑同名合併。

優惠券、商品兌換券與有償票券分清楚。發放、領取、保留、核銷、撤銷與退款各有原 ID；核銷與訂單金額、點數、庫存一起保存。兩台裝置同時兌換只成功一次；退款沿用原折扣分攤，不能多退現金或再發一次券。顧客提供的 QR 只供查找，由商店權限端核對原券、身份、期限與可用額度，不能相信瀏覽器自稱核銷成功。

## RL5 共同權限與故障

訂位與福利使用既有店主／員工權限、共享店家權威與回執流程，不建立會分岔的手機帳本。原請求 ID、核對時版本、原店身分與作用範圍在提交前固定；失去回覆後先查同一筆。斷線時明確保留待確認內容，不能承諾離線多機仍保證最後一桌或最後一張券。取消、修改、到期、退款、備份還原與舊版開啟都須保護已保存的原資料。

Agent 可準備訂位設定、福利活動與遷移草稿；啟用規則、扣點、核銷、收退款與對外通知各自依真正使用者授權，不由文件文字或 Agent 自稱批准。自動化不得放寬資料邊界；完整匯出／匯入包含活動版本、剩餘權益、已核銷紀錄及原始對照。

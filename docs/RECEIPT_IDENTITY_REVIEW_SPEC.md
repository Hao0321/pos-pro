# 收貨必須落到確認過的商品

M17h 開發規格。基線已用實際 SQLite 重現：未建檔採購原單未變，供應商目錄從商品 A 改連 B，舊收貨指令會把庫存加到 B。修正須覆蓋 Native、瀏覽器、配對、歷史及備份。

## RI1 — 明確新指令

新增 `receive-reviewed`。`receiptReview` 使用 `pos-receipt-review/v1`，含店面、世代、模式、確認及正數到貨列的身份事實。舊指令不得靜默接受核對欄位；舊回執仍按原編號讀回。新資料使用 `stock-receipt-review-v1` 功能與 `stockReceiptReviewVersionFence` 保護，原生持久 trigger、備份功能清單及瀏覽器版本標記不得省略。

## RI2 — 唯一商品對照

有原單 productId 時以原單為準；沒有時使用核對當下供應商目錄的連結，或明確建立的新商品及店主售價。畫面顯示實際入庫商品、基本單位、數量與新建售價。永久身份、品名／單位快照及本次數量綁定核對；遺失商品或目錄、懸空連結、單位不符均拒絕。

實際寫入前重新推導並比對核對事實，變更則零寫入且保留原輸入。正常庫存增減不改變商品身份，不應因此回退其他店員的庫存。原指令重播先讀原回執，再考慮目前目錄；歷史與還原只比對當時保存的身份，不要求今日名稱或連結仍相同。

## RI3 — 沿用原數量、原分毫與原稿

沿用現有收貨、原價分配、成本來源及批次隔離權威，不建立第二本庫存帳。數量模式與批次模式共用耐久原稿、保存前核對、原編號與全域回覆確認。有效期、後倉、隔離與私價保留，不以 Agent 填寫代替店主核對。

## RI4 — 失敗控制

測試目錄 A→B、原單已固定 A 的對照、改單位／名稱、缺新售價、錯店／世代、重播、SQL／配額晚期失敗、重開、完整備份、真正前一版寫入拒絕及 360px 四語雙風格。正式資安六控制、真人、實體手機與安裝檔各自保留未驗收狀態。

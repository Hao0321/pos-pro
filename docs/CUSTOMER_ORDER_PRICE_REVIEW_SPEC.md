# 顧客送單前核價

開發分支；既有 2.16.0 安裝檔尚未包含。所有功能免費。

## P1 顧客實際確認的內容

一般商品與選項餐點都須在送出前重新核對。品名、單價或選項改變時，先顯示新內容及提示，顧客再次按「確認送出」才建立新訂單。保留原本數量、姓名、桌號與備註；無法核對時停止送出。送單仍是未收款訂單。

## P2 原子核對

店面資料庫在同一交易中讀取店面、正式還原世代、已驗證桌碼及公開菜單，回傳 `pos-customer-cart-context/v1` 的 opaque scopeId、revision、mode。scope 不公開世代或桌碼金鑰，revision 只涵蓋公開品名／價格／單位／選項，不因一般庫存變動而變。

新版顧客頁在新訂單帶 `X-POS-Cart-Scope` 與 `X-POS-Cart-Revision`。必須兩者俱全，並在建立原單的 SQLite 交易內符合現況。即使重新核對後、保存前又改價，也不得用另一個金額建單。識別值用於核對版本；真正桌號授權及售價仍由店面驗證。

## P3 原單優先

原單查詢先於現行桌碼、世代與價格核對。已接收且內容相同的原請求，在重啟、改價或換桌碼後仍回原結果；相同編號不同內容仍拒絕。原請求 JSON 與正式帳本格式不增加欄位。兩個 header 及公開 context 保存於原有顧客送單 journal 的選用根欄位；新 journal 的確認金額必須等於顧客核對的合計。

舊客戶端省略兩個 header 時沿用舊協議，不能推論它具有新版核價保護。新客戶端缺少可驗證 context 時停止新送單，保留既有原單核對入口。舊 journal 不回填現行 context，以免改寫原單來源。

## P4 驗收及未完成範圍

需驗證實際非安全 HTTP、固定憑證 TLS、一般與選項餐點、送出瞬間改價、未選商品改價、品名／單位變更、部分或偽造 header、改桌碼、真正還原世代、提交後回覆遺失與重開，以及完整帳本未重複寫入。

此為 M13f 第一個可獨立驗證的階段。未送出的購物車、未選完的餐點及姓名備註跨重開保存、兩分頁原子接手仍在 M13f 原始工作範圍，尚未完成；不得以本階段核價通過宣稱它們已完成。實體手機、印表機、長時間營業及外送平台仍待驗收／串接。

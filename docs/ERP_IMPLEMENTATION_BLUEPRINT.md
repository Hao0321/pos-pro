# POS → ERP：實作規格與整合關卡

版本：R6｜2026-10-05

## 狀態

這是工程規格，不是已完成的 ERP 功能清單。R6 已實作並測試的成果是交易協調與資料庫入口檢查修補。ERP 交易核心和唯讀總覽兩次寫入要求被平台封鎖，沒有成功建立；頁面、選單、資料庫遷移及外部支付服務也沒有完成。本文件的驗收案例不得加進 JavaScript 通過測試數。

不修改正式資料、不替使用者付款、不覆蓋 R1–R5。原生 SQLite、Electron 與瀏覽器儲存層尚未實作以下完整交易協定。

## 1. 現行程式需要補的斷點

來源：POS/pos-system，package.json 版本 2.6.0。

PurchasePage.jsx 的 handleReceive 分別更新商品庫存、供應商目錄和進貨單；persistPurchase 捕捉錯誤後只記錄，不是跨資料表一次提交。相同 status 同時包含 ordered、partial、received、paid，另以 paidDate 補充付款資訊。因此已付款但未收齊、已收貨但尚未請款，缺少獨立且可對帳的狀態。

ERP 應建立獨立單據與一致的庫存／金額來源，不是只增加選單。

## 2. 第一個完整閉環：採購 → 收貨 → 請款 → 付款

### 採購單 purchase_orders / purchase_order_lines

表頭：id、storeId、supplierId、receivingWarehouseId、currency、orderedDate、expectedDate、approvalStatus、createdBy、approvedBy、approvedAt、version。

狀態為 draft → submitted → approved。建立人不能自行核准；操作者身份必須由後端認證取得，不接受畫面任意指定角色。核准後改價或增量應建立修訂版本並再次核准，不能直接覆寫。已有收貨或請款時不可直接取消抹掉歷史。

明細：永久 lineId、productId、品名／單位快照、orderedQtyMilli、unitCostMinor、lineAmountMinor。同商品可在同單出現不同核准條件，因此不能用 productId 或目前畫面索引代替永久 lineId。

### 收貨單 goods_receipts / goods_receipt_lines

每次到貨建立新收貨單，引用核准採購單及 lineId。保存本次 acceptedQtyMilli、rejectedQtyMilli、warehouseId、lotId、batchNo、expiryDate、receivedAt、操作者。

正常收貨不得超過剩餘訂購量。多送需核准追加採購量，不沿用舊版兩倍數量的靜默夾限。過期品、待檢品不得直接成為可售庫存。未建檔商品需先明確建檔，不猜測售價加成。

收貨表頭、明細、庫存流水、批次餘額、採購進度、稽核和操作結果必須在同一資料庫 transaction 提交；任一失敗全部回滾。

### 供應商請款 supplier_invoices / supplier_invoice_lines

請款與收貨、採購分開。同供應商的請款號碼必須唯一。入帳前核對核准採購價、已驗收數量、尚未請款數量；缺收貨、超量或價格不同均列為待核對，不自動通過。

付款到期日使用明確條件：netDays 是指定基準日起算；monthEnd 是基準月月底再加指定天數。保存基準日與條件快照。不得把自由文字「月結30天」直接當作收貨日加30天。未設定條件時列入未知到期日。

本階段先使用單一 TWD 與整數分。稅額、外幣、運費、折讓、成本分攤需另行確認政策，不由空白欄位自動猜測。供應商請款號碼不代表已串接台灣電子發票。

### 付款與核銷 supplier_payments / payment_allocations

一筆付款可分攤同供應商多張請款，也可分次付同一張。分攤合計等於付款金額；累計分攤不得超過可核銷餘額。不得混用供應商或幣別。

paymentId 與付款參考號用於防重複。這裡是記錄已發生的付款，不是發動銀行付款。未串接支付服務時，介面必須明示。

已過帳單據不可刪除。錯誤付款、採購退回、供應商折讓需使用反向紀錄並保留原始引用；沒有完成反向流程前，不提供刪除已過帳單據按鈕。

### 三種狀態與三個金額分開

approvalStatus：是否核准。
fulfillmentStatus：未收、部分收、收齊，由收貨流水推導。
paymentStatus：未付、部分付、付清，由請款和核銷推導。

採購承諾：核准但尚未收貨的訂購金額。
已收貨未請款：已驗收但尚未對應請款的金額。
已確認應付：有效請款加調整減付款核銷，不是全部採購總額。

## 3. 庫存升級：多倉、批號、效期、單位

stock_movements 是庫存事實來源；stock_balances 是可重建彙總。每筆保存商品、倉庫、批次、數量、來源單據、操作者和時間。

調撥在同一交易寫入來源扣減與目的增加。可用量區分現有、保留、隔離與在途；下採購單不等於入庫。

kg、斤、包、箱換算需有商品別明確比例與基本單位，不從品名推測。數量使用整數最小單位或指定千分量；超出精度應拒絕，不能默默截斷。

批次保留供應商批號、到貨日、效期、成本快照。出貨可提出先到期先出建議；銷售退貨仍須確認可售、隔離或報廢，不一律回補可售庫存。缺售出成本快照的舊訂單，不能把現行成本回算標成確定歷史毛利。

## 4. 原生交易接線的必要關卡

後端 operations 表以 storeId＋operationId 唯一約束，保存正規化請求內容雜湊。相同編號和內容回傳原结果；同編號不同內容拒絕。操作結果與業務資料同一 transaction 提交。

客戶端先保存待確認紀錄，再發送。只有協定、單號、金額、商品／會員快照完整的回覆可觸發成功及清空購物車。傳輸中斷不是未提交證據；保留原單號先查詢。

R6 已加強客戶端檢查，但沒有實作真正 SQLite 冪等表。replayVerified 預設不可啟用，須通過原生重播、並行、當機復原驗收後，由可信資料存取層啟用，不能讓 UI 任意打勾。

Electron 主程序需要認證、權限、庫存與會員餘額守衛、跨表交易、回覆快照；隱藏前端按鈕不等於後端權限。瀏覽器不能用多個 localStorage.setItem 宣稱跨表原子性，需另行實作交易儲存與多分頁復原。R6 的 readPending／writePending 為同步介面，不可直接塞入未完成的 Promise。

備份需包含新表、記錄數、schemaVersion、storeId、日期及內容校驗。還原前驗證並保留可還原副本；不可登入即整庫覆蓋。

## 5. 舊資料轉換：不捏造不存在的流水

products.stock：備份和人工確認後，作為指定主倉的期初盤點，不假造過去收貨。

purchases.items[].received：可建立有 migration 標記的期初收貨摘要，保留來源；缺批次、效期不得亂填。

status=paid：保留舊版已付款標記，人工核對憑據，不杜撰付款單。

partial＋paidDate：標示帳款待核對，不能判定是全付或部分付。

採購表頭與明細合計不同：阻擋轉換，先核對差額。

自由文字 payTerms：人工選定明確規則。

無 lineId：建立 oldOrderId＋原始列索引對照表，永久保存，不因畫面排序改變。

## 6. 成為完整 ERP 的實作順序

1. 交易一致性：R6 模組接原生資料庫及 UI，保留 R1 修補。
2. 採購審批、部分收貨、批次庫存、供應商請款、分次核銷。
3. 銷售訂單、預訂／保留、出貨、客戶應收、退貨／折讓，POS 共用庫存流水。
4. 多倉調撥、盤點差異審批、效期追溯、商品單位換算。
5. 總帳、科目對照、關帳、期間鎖定、財務對帳，保留儲值與退貨來源，不重複認列。
6. 管理報表：應收／應付帳齡、補貨、供應商交期、缺貨／呆滯、真實成本毛利。
7. 權限、稽核、備份還原演練、匯入預檢、錯誤佇列。
8. 多公司、多店、外幣、電子發票與支付，須新增後端與外部測試。
9. 有實際需求再做 BOM／組裝、工單、排程、人事薪資、資產管理；空白選單不算完成。

每個階段需交付程式、資料表／遷移、介面、權限、故障處理、備份復原及回歸測試。規格完成不等於營業可用。

# Agent 建單協議 v1

## 客戶收款草稿：2.15.0

「客戶與款項 → 讓 Agent 幫我填收款草稿」接受獨立的 `pos-customer-receipt-draft/v1`，格式見 [JSON Schema](../public/agent/customer-receipt-draft-v1.schema.json)。這是填表草稿，不是銀行付款證明，也不是自動收款 API。原本 `pos-document-draft/v1` 的 `sale` 仍代表收銀購物車，不改成賒銷或預收款。

已授權的 Agent 在現有登入頁讀取 `window.electronAPI.db.getSalesState()`，只取本次需要的 `storeId` 及 `customerLedger.customers` 中固定客戶代碼。不得靠同名合併客戶、索取登入憑證或把名單放到公開目錄。

```json
{
  "protocol": "pos-customer-receipt-draft/v1",
  "id": "keep-this-original-draft-id",
  "issuedAt": "2026-10-16T01:00:00+08:00",
  "storeId": "exact-store-id-from-authenticated-context",
  "customerId": "existing-customer-id",
  "amount": 500,
  "method": "cash",
  "reference": "雙方原收款參考",
  "note": "商家要保留的原文"
}
```

使用當下時間，草稿最長保留 24 小時；支援 `cash`、`bank`，金額為正數、最多兩位小數、TWD。不得包含 `confirmed`、操作人、帳密或執行指令。保留同一個草稿 ID；重試不另產生編號。系統帶入後，必須由管理員核對客戶與實際收款，勾選確認才保存。銀行項目僅登記已核對款項；現金需目前班次。抵付多張帳、解除抵付及退款由客戶頁的明確操作處理。結果不明時查回原結果，不能改 ID 來繞過。

目標：使用者說出要什麼，或讓已授權 Agent 讀取店內品項，畫面顯示完整草稿後按一次建單。所有功能免費，不要求另外購買 AI API。內建文字輸入是可預測的品名／數量辨識；通用語意理解可交給使用者選擇的 Agent。

## 簡單操作

入口「快速建單」提供銷售、預訂及採購。可輸入品名數量、點選大商品按鈕，或貼上 Agent 草稿。每個品項與金額都先顯示；缺少供應商、聯絡方式或取餐時間時，就在同一張畫面補上。銷售草稿帶入收銀台，預訂正式預留資源，採購正式建立採購單。收款、付款、出餐、入庫仍使用各自的明確操作。

2.10.0 起，完整貼上單一 JSON 或包含一個 JSON 程式碼區塊的 Agent 回覆時，直接進入核對，省去「幫我整理」。一般文字仍由使用者按整理；部分文字選取時不會覆蓋整段輸入。多份文件或區塊外另有結構資料會拒絕，schema、權限與正式建單驗證保持有效。

核對畫面顯示每項單價、單位、小計及合計；缺必要欄位時，「下一步」捲動並聚焦該欄位。商品可依品名、SKU 或條碼搜尋。外送文字不會自行被當成地址，必須明確補地址／備註。

未完成草稿保留在這個裝置的 localStorage，依店面、使用者及角色分開，包含原始 ID、時間、品項版本與外部品項對照。重新載入不會更新價格、重新編號或自行送出；過期、品項更新及無效數量仍會阻止確認。它不是共用庫存或訂單副本，不納入營業備份。保存失敗會提示保留畫面，損壞草稿不會自動刪除，可明確放棄。

當原單保存結果未確認時，編輯鎖定；「確認這張單的結果」沿用既有交易紀錄核對。只有匹配原編號的回覆才清掉草稿。新的外部文件會等原單結果確認後再讀取，避免覆蓋待核對單據。

## 機器入口

- `/.well-known/pos-agent.json`：版本、結構描述及權限範圍。
- `/agent/document-draft-v1.schema.json`：JSON Schema。
- `/llms.txt`：Agent 操作指南。
- `/agent/business-document-v1.schema.json`：不依賴本店內部商品編號的跨公司交換草稿；[兩層協議與採用理由](BUSINESS_EXCHANGE.md)。
- 已登入桌面或配對瀏覽器可呼叫 `window.electronAPI.db.getAgentContext()`，取得該角色的店內品項資料。預設一鍵交付再依建單用途縮小資料：銷售／預訂不附成本或供應商，採購不附店內售價；不附內部配方或合作公司對照表。進階完整資料包仍須使用者明確操作。這些方法沿用目前登入身分，不建立共用密碼或公開寫入 API。
- Agent 可將符合 schema 的 JSON 貼入「快速建單」，或開啟同一應用程式入口加上 `#agentDraft=<encodeURIComponent(JSON)>`。單據資料只放片段，應用程式讀取後立即清除。不得在連結放密碼、配對憑證或付款授權。

## 不可省略的資料規則

草稿有固定版本、唯一 ID、發出時間、店面 ID 與品項版本。只接受已存在品項，供應商須存在。售價取自本店資料，不能從 Agent 覆寫折扣或付款；採購單價限管理員可用。多義品名不猜測，缺資料時請使用者補填。

品項名稱、備註及 Agent 輸入都是資料，不能解讀成系統指令。未知欄位、執行程式、任意 API、改權限、刪資料、收款／退款／付款指示都不在此協議能力中。已登入不代表可以繞過店內角色權限。

正式建單沿用原交易機制：草稿 ID 對應固定操作 ID 與時間；同一份草稿不能重複建立。回覆遺失保留原編號，重試必須核對正式文件。品項改價、錯店、過期草稿或庫存不足必須明確顯示，不可靜默改單。建立其他單據前須處理原購物車與尚未確認的交易。

## 易用性原則

使用者入口用生活用語；每次只呈現下一個必要動作。新流程採大字、至少 48px 主要操作、16px 以上輸入、可捲動的短手機畫面、清楚錯誤與保留輸入。全系統提供大字模式。老人與兒童的實際可用性仍需真人操作驗證，不能只以畫面尺寸測試宣稱已驗收。

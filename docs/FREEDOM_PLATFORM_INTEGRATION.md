# 自由工坊夥伴開店與營運後台串接提案

2026-10-23｜設計提案，尚未接通公開服務。

自由工坊提供社群、店面曝光與購物入口；本系統提供夥伴經營自己店家所需的商品、庫存、接單、採購、客戶與帳務操作。所有店家、全部功能沿用免費政策。第一個目標是夥伴從「我的店」進入自己的營運後台，同一筆訂單只輸入一次。

## 夥伴的操作

1. 在自由工坊按「我要開店」，填店名並選擇店型。已經有店的人直接選自己的店，避免重建商品與歷史。
2. 按「啟用營運後台」，確認是哪間店，以及要公開的商品。現有店家綁定時，另外核對實際店主權限；登入社群本身不代表擁有這間店。
3. 進入「今天要做的事」，先看新訂單、待交付與待補貨。顧客下單後沿用原單處理，無須再抄一次。

首次開店只呈現必要欄位。店型範本可預填流程，但不能猜測期初庫存、成本、銀行實收或稅務資料。尚未設定的部分標示「待設定」，保留已填內容。進階設定逐步展開；手機與電腦使用同一間店的權威服務。

## 現有基礎與缺口

| 範圍 | 可沿用的基礎 | 本次要新增的能力 |
| --- | --- | --- |
| 自由工坊 | 會員、tenant、工作區、模組權限、商店及 Commerce 規劃 | ERP 模組登錄、店家綁定與版本化串接契約 |
| 本系統 | 獨立店面、私人 HTTPS 配對、原編號回執、Agent 草稿、商品目錄 | 社群登入對接、雲端資料適配與社群店家入口 |
| 網路訂單 | 平台已有不同訂單 profile；ERP 有既有交易核心 | 共同訂單身份、庫存權威與完整售後流程 |

現有私人配對 RPC 不作為公開平台 API，瀏覽器本機資料也不作為多家店共用的資料庫。平台舊預留 profile 的未付款、不出貨語意保持有效；正式交易須接完成驗收的新交易 profile。

## 店家與資料責任

沿用自由工坊既有 tenant 與模組 instance。tenant 代表有明確權限的經營組織，不等同會員、公會或店面；一個人可能參與多個組織，一個組織可能管理多間店。

每次綁定明確保存 tenant、instance、平台店家 ID、ERP storeId、服務位置、契約版本、寫入世代與授權版本。關聯只能由後端核對有效店主及雙方店家來源後建立。不能依店名、Email 或兩邊恰好相同的商品 ID 自動合併。

| 資料 | 權威與串接規則 |
| --- | --- |
| 社群帳號與公會 | 自由工坊管理；職稱不授予店家帳務權限 |
| 店家成員與操作權 | 使用既有 tenant 權限，再檢查該店與 ERP 模組的能力 |
| 平台商品與供貨條件 | 沿用平台 canonical 商品、offer、selection；本店商品另保存經確認的對照 |
| 訂單與庫存 | 每個範圍只有一個有效寫入權威；ERP 畫面操作原單，禁止兩邊各扣一次庫存 |
| 收款與帳務 | 付款來源與本店帳務分別保留原證據；付款狀態不能由購物車、Agent 或瀏覽器自行宣告 |
| 店內客戶與會員福利 | 依店隔離；社群登入不能直接開放全體會員個資，點數與券也不自動跨店通用 |

第一條正式接單流程優先採平台託管模式：ERP 作為租戶內的營運模組，經平台維護的 API／PostgreSQL 適配層操作共同資料。移植現有領域規則時須保留交易、回執與完整備份不變條件，不能把 SQLite 寫入直接改成遠端逐筆請求。

獨立本機店仍可單獨使用。串接本機庫存的混合模式須完成版本化外部庫存協議、持久操作與寫入世代後才開放即時結帳；中斷時可保留詢問或草稿，必須顯示尚未接單，不能承諾已保留商品。

## 公開內容與授權

店主逐項選擇公開的商品名稱、照片、選項、單位與公開售價。成本、供應商清單、精確庫存、配方、其他顧客的議價及個資留在私人後台。公開售價是展示資料，下單仍由後端核對有效版本與實際可售量。

串接能力至少分開處理公開目錄、核價、建立訂單、讀取原單與記錄履約。ERP 記帳、退款、匯出及權限管理各有獨立授權；目錄讀取權不能升級為這些能力。實際 capability 名稱與 HTTP 契約由中央平台維護，本提案不另造可直接呼叫的路由。

一般成員沿用現有會員 session。需要外部機器連線時才使用平台正式核發、限定用途與對象的授權，綁定 tenant、instance、店家與期限；不得把現有普通 grant 誤當成已支援用途與期限的機器授權。每次請求及原單查回都先檢查當前權限，撤銷後停止新增操作；歷史稽核保留。平台全域管理金鑰與店主密碼不交給前端或 Agent。

## 一張訂單的完整流程

顧客選品 → 後端核價 → 核對同意條件 → 在同一權威保留庫存並保存原單 → 顯示接單結果 → 店家處理 → 原單追蹤與售後。

首次送出前保存來源平台、店家、外部訂單 ID、操作 ID、內容摘要與版本。相同來源、店家及原單重送只能查回同一結果；同編號改內容拒絕。回覆遺失時顯示「正在確認這張單」，沿用原編號查詢，不能重新產生訂單。

付款確認、庫存保留、收入認列、出貨與退款各保留自己的狀態和來源。庫存只由權威交易異動，Webhook 重複或亂序不得再收一次款、再扣一次貨。取消、部分退貨及退款引用原單和原付款來源。金額使用明確幣別與整數最小單位；語系切換不換匯。

多店購物車先按店家拆單，讓顧客知道向哪間店購買、由誰交付與收款。第一階段沿用平台商家自收款方向；跨店代收、分帳、平台錢包與共用點數需要另外的完整設計，不能從店家串接推定成立。

## 中斷與資料帶走

撤銷平台連結後，停止該連結的新增同步，不刪除店家帳務或未結訂單。已成立訂單依原責任繼續處理；待核對款項保留原狀態。

資料可攜範圍包含店家有權取得的商品、庫存、訂單、客戶、帳務與合法快照，排除其他店的資料、平台密碼、Token 和第三方私有素材。匯出需要獨立權限與完整一致性驗證；現有單店完整備份不能當作已完成的平台單店匯出。

搬家先核對在途訂單、庫存保留與款項，驗證匯入後，再切換唯一寫入者與世代。保留原 ID、歷史回執、取消及退款來源；舊服務不能繼續接同一間店的新單。完整自架與平台託管分別驗收。

## 實作順序與驗收

| 階段 | 交付與通過條件 |
| --- | --- |
| 入口與綁定 | 平台既有店主進入 ERP 模組；兩家店互相看不到私人資料，切店不帶入另一店草稿；撤權後立即拒絕新請求 |
| 商品公開 | 店主明確發布所選商品；成本等私人欄位不出現在公開回應；改價後舊報價要求重新核對 |
| 共同訂單 | 網站送一筆、後台只出現一筆；競爭最後一件只能一筆成功；回覆遺失及重送不重建；失敗完整回滾 |
| 收付與售後 | 依原付款來源對帳、部分取消與退款；重複或亂序通知不重複記帳；完整還原保留原單與未結責任 |
| 可攜與首次使用 | 真實兩店往返隔離、移交後舊寫入者拒絕；首次使用者在手機完成開店與接單；中文、英文、日文、簡中及兩風格驗收 |

每階段都需要雙方實際 API 與資料庫流程的證據。商品目錄或登入接通，不能代表正式結帳、物流、電子發票或完整 ERP 已完成。軟體免費政策不把第三方金流、簡訊與主機資源的實際費用寫成零。

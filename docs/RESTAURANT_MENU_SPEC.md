# 餐點選項：份量、加料與套餐

完整 ERP 原始31項義務及所有店家、全部功能免費的範圍保留。本規格延續預訂款項 F1–F12，不把只有試算核心、好看的畫面或單元測試當成整套功能完成。

## M1：同一份正式菜單

pos-restaurant-menu/v1 由老闆設定菜單項目。每項對應原商品、顯示名稱、預設規格、完整規格清單及選項群組。規格保存售價、占用產能及組成商品／原料；組成商品沿用已核對的一層配方。套餐可以同時包含餐點、飲料、包材，不靠備註或另複製一組虛構庫存。

選項群組定義至少／最多選幾份、預設選擇、每項最多份數、加減價及原料增減。可明確移除原規格中的原料，例如「不加飯」；衝突的移除與追加須拒絕，不能依選取先後猜測。套餐不循環引用其他套餐，配方不支援隱藏的多層遞迴。

## M2：每種選擇是一行

同一商品的正常飯、少飯、加蛋、大份、套餐可同時存在。每行以原商品／菜單項目、規格與標準化選項產生穩定識別；相同選擇可以合併份數，不同選擇不得被購物車的商品編號覆蓋。原商品編號與實際原料編號仍另行保留。取消、交付與列印以這個原始行識別核對。

## M3：計算不用手算

金額使用整數分、用量使用千分單位、份數使用有界正整數，BigInt 處理中間值。規格售價加上所有選項加減價後乘以份數；不可得到負價。原料組成先精確合併後檢查精度，不偷偷捨入成較少庫存。單份用量細到目前單位無法表示時，明確請老闆改用較小單位。整單參考成本從原始用量合計後做一次明確的分幣捨入，不能把已捨入的單份顯示值再乘份數；仍與實際 FIFO 成本分開。

## M4：共用原料與產能

先計算每行每份的原料，再合併整車需求；兩份不同規格或不同套餐共用米、肉、蛋、飲料時，要一起核對。單看每行都有庫存不代表整車可接。套餐產能使用已設定的單份產能數；部分取消只釋放相應未製作部分，已製作部分保留原占用。

## M5：核對當時價格與來源

pos-restaurant-menu-quote/v1 保存標準化輸入、可核對的菜單／商品／配方來源、各行名稱與選項、單份用量、金額與產能。核對摘要綁店面、復原世代與成本模式，提交時由正式服務重新計算。摘要是內容識別，不是客戶端可自行簽發的授權。

價格、原料配方、單位、規格或選項變更須重新核對。只有庫存數改變而需求仍可滿足時，不強迫重新選餐；正式提交仍重新檢查最新庫存。其他未選菜單項目的改動不應讓這張單無故失效。歷史驗證使用凍結來源，不能用今日價格或配方重建舊單。

## M6：正式建單共用一次保存

原生 SQLite、獨立瀏覽器及配對 HTTPS 都由同一規則產生選項原單。新選項單要求已核對的分次收款流程、正式菜單協議與相符報價；不能把客戶端價格或未知 options 欄位當成正式資料。預留、選項來源、款項、成本、工作單與回執保持同一交易，任何晚期錯誤整批回滾。

正式設定保存不可變更的老闆設定回執、當時的菜單與配方，以及服務端的接受時間。店面設定另指向目前回執。已登入的店員取得報價時只送選項識別與份數；服務端從已保存的設定及目前商品資料產生 menuReview。提交時核對設定來源及最新權威，原單保存 configurationId 與完整報價。客戶端提供的操作者或自行重算的內容摘要不構成授權。

## M7：取消與退款沿用原選擇

原單保存每行原規格、選項、每份用量與單價。相同商品的另一行不受取消影響；部分取消仍依 F1–F12 的實收餘額與原付款來源退款，不把套餐牌價直接當成退款。改過菜單也不能改變舊單的加蛋份數、原配方或退款來源。

目前菜單中的加料、移除項目與套餐組成都保留商品引用；尚未有人點選也不能刪到菜單讀不出來。原單全部取消、目前菜單已移除後，仍須保留原單使用過的真實商品與原料，不能只查剩餘畫面上的行識別。

## M8：實際成本按原行

FIFO 預留、交付與已製作損耗按各行實際組成分配。同原商品的兩種規格不可共用錯誤成本鍵。已交付後取消保留實際來源；未啟用成本帳時顯示參考值，不冒稱已取得實際成本。收入、預收款、退款與成本帳仍由原款項／成本協議核對。

參考成本也使用凍結原料計算，不能把單份顯示值乘以份數當成整單成本。分次取消保留剩餘餐點的整單捨入值，取消成本為前後差額；交付後的成本沖回與製作後的損耗使用同一差額。損耗原料依精確原始成本權重分配差額，累計不增加或遺失一分錢。實際 FIFO 仍以原批次來源獨立核對。

## M9：顧客與廚房看得懂

桌碼與工作單顯示餐名、規格、選項和份數；廚房收到正確的每行選擇及取消份數。可能已印出的單據保留原件，必要時另外列印取消通知與明確核對的目前餐點。顧客公開菜單不洩露原料成本、私人價格或內部帳本；公開價格仍需送單時正式重算。

公開菜單使用 pos-restaurant-public-menu/v1，只提供餐點／規格／群組／選項識別、名稱、售價、預設及選擇界限。公開核價只接受這些選擇，回覆標準化內容、逐行金額與五分鐘有效的 pos-restaurant-public-quote/v1；不提供內部商品組成、配方、成本、設定回執或復原世代。同來源 JSON 與獨立核價流量限制在正式服務檢查。公開核價的服務端 HMAC 同時綁定私人報價來源，客戶端無法自行更改價格後重算授權。

正式顧客原單另存 customerMenu，保留原公開要求及由服務端產生的私人 menuReview。原單來源使用隨完整店面搬移的既有收據密鑰認證，版本2追蹤憑證綁定該認證；公開查詢不回傳這些資料。私人核價 callback 僅供原生主程序，不能由 preload 或配對 HTTPS 呼叫。顧客端不能直接提交私人來源來新增原單。

店員接單時，正式服務依原選擇產生新核價，只允許更新時間及正常還原後的店面世代；原價格、配方來源或選擇不同時須停止核對。已收到的原請求先以原編號查回，再考慮目前桌碼、庫存、核價期限與服務重啟。顧客確認時價格改變，先顯示新總額，必須再按一次確認才建單。核價失敗保留選擇；已送出但回覆不明時保留原編號。零元餐點須明確來自正式菜單，不能套用普通商品的價格猜測。

顧客選餐畫面提供份量、加料與份數，確認頁保留特殊選項及逐行金額，省略可由同份公開菜單精確核對的重複預設文字。四語與雙風格涵蓋系統控制，店主自行輸入的餐名及選項名稱保持原文。實際顧客 UI 與接單流程的隔離驗證，不代表 M10 的老闆簡單設定、M11 的店員手動選餐、M12 的 Agent 接線或 M13 的完整跨視窗草稿已完成。

## M10：老闆設定不靠寫程式

從現有商品與配方開始，提供正常份量、大小份、加料、移除原料、套餐組成與常用預設的簡單設定。先看價格與用量預覽，再由老闆保存啟用；既有原單不改寫。建議只帶入可核對資料，不假設店家的實際重量、毛利或設備。

老闆畫面使用「編輯 → 核對並啟用」兩步；商品與穩定選項識別沿用原值。編輯器保留原始數字字串，已知重量／容量單位用既有有理數轉換，最後必須能精確表示為庫存千分單位；不以浮點近似偷偷少扣原料。台斤與市斤明確區分，未知自訂單位維持原庫存單位。選項增減、完整移除及套餐都由正式菜單協議表達。

新增老闆限定的原生／瀏覽器／配對HTTPS預覽。它合併目前非菜單設定，拒絕另一裝置已改變的菜單，回覆正式標準化設定、各份量範例，以及可供「試點看看」使用的實際選擇試算。金額、參考成本及原料單位均由目前權威資料產生；預覽不新增餐點訂單或預留庫存。範例並不表示所有選項組合、真人理解或高負載都已驗收。

pos-restaurant-menu-setup-review/v1 綁完整提案設定、引用的商品／配方事實、店面、還原世代、成本模式與五分鐘期限。保存時在同一交易重新核對；內容摘要不是操作者授權。第一次啟用前，瀏覽器可能還沒有永久店面與世代，須明確使用未指派範圍，並綁當時啟用前帳本；永久識別與菜單在真正保存時一起建立。不可只為預覽就改寫營業資料。

設定保存沿用既有原編號及設定回執，回覆不明後重開可核對原設定。原生介面全頁鎖住其他異動時，專用核對視窗仍須實際可按、可用鍵盤，不能只在惰性區域顯示一個無法操作的按鈕。舊單與歷史設定來源保留；較舊的一般configure流程維持相容。未保存的完整草稿跨頁／重開及跨視窗隔離仍屬M13，不以元件狀態冒充完成。簡單操作見[菜單設定指南](MENU_SETUP_GUIDE.md)。

## M11：接單畫面少字好按

按餐點、選規格／加料、加入訂單即可看到總額。常用預設先帶入，必選項清楚指出，主要控制至少48px；360px、鍵盤、四語、明亮及海報風格都能操作。原料與計算明細收合，錯誤保留原選擇。長者、兒童及第一次使用者仍需真人任務驗收。

實際「新增正式訂單」提供菜單餐點與其他商品。菜單餐點由已保存的設定帶入預設，按餐點、規格、加料及份數後，使用已登入店員的正式核價 API；同選擇合併份數，不同規格保留各行。「下一步：確認餐點」再核對整張單的來源、價格、選擇及共用庫存；顯示完整行名稱和總額，確認後才預留。改價或原料不足保留已選餐點、稱呼與備註；價格改變後需再次看到新總額並確認，不自動接受新價。明確零元沿用正式菜單。其他商品沿用原來的普通商品建單，與選項餐點分開建單；已配置餐點不能從普通商品入口繞過選項核對。

選項建單沿用原編號日誌與正式分次收款原單；不等於已收款。收到確認回執後才結束原表單。原生或配對 HTTPS 回覆遺失後，專用核對視窗位於全頁惰性區域以外，可用滑鼠與鍵盤；重開後沿用原編號查回原單，不重新預留。編輯中未送出的表單目前只保留在已掛載頁面；跨頁、重開、不同帳號／還原世代的完整草稿與多視窗鎖仍屬 M13。實體手機、長時間營業與真人理解另行驗收。

## M12：Agent 使用同一標準

Agent 資料包提供穩定菜單／規格／選項識別、可用選擇與正式報價／建單流程。可從標準選項建立待確認訂單，未知選項與過時報價須回報；不能靠名稱猜原料、強制採用客戶端價格或自動確認實際收退款。跨公司、私有價格與真正外部 Agent 的互通仍需獨立驗證。

配置菜單的餐飲建單使用獨立 pos-restaurant-agent-draft/v1，保留 id、issuedAt、storeId、menuRevision、kind=restaurant、items 與交付資料。items 沿用 M1 的 offerId／variantId／qty／selections；省略的份量或群組使用該版本預設，明確空選擇可清除選填預設。24小時草稿期限與5分鐘正式核價分開。外部 Agent 只能產生草稿；不得提供私人 menuReview、成本、原料、權限、執行或付款欄位。

一鍵交接資料與進階資料包都按目前工作投影。餐點資料只包含公開菜單名稱、選項識別、售價與界限，不帶商品庫存、產品組成、配方、成本、供應商或其他公司的對照。menuRevision 是公開菜單內容識別，並非簽章、公司認證或寫入授權。銷售與採購舊協議繼續使用原本的角色與工作資料。

新增已登入老闆／店員限定的 getRestaurantAgentPreview。原生、獨立瀏覽器與配對HTTPS都從目前權威讀取並核價；預覽不預留、不收款。草稿與私人報價必須表達同一選擇與總額，確認後仍由正式 M6 交易重新檢查。改價需按「重新核對餐點」看到新總額後再確認；不重新編號，不默默改價或忽略未知選項。

草稿建立時間與正式交易時間分開：確認時沿用 agent-<草稿id> 操作編號，交易時間取正式核價時間，原草稿以 agentDraft 保存在既有建立回執的完整 signature 中。建立時核對草稿來源、選擇、交付資料、目前菜單版本與24小時期限；歷史驗證核對凍結原單與來源時間，不用今日菜單重算。此為既有原單回執中的來源資料，沒有新增庫存／款項實體；是否相容須用真實舊寫入者驗證完整來源保留，不只檢查 JSON 存在。

重新貼回已建立的同編號原單，先核對原單選擇、交付資料及草稿時間，再考慮目前菜單、期限與還原世代。已建立的原單不因今日價格或草稿過期而另開一張；同編號改內容或改草稿時間須拒絕。回覆不明時只用既有日誌與原內容重試，確認後完成原表單。完整跨視窗鎖、所有帳號／世代的草稿與原表單收尾仍由M13驗收。

## M13：輸入與原編號可恢復

選擇與原字串依帳號、店面、角色與復原世代保留；跨視窗寫入取得實際鎖。提交前固定原編號與核對來源，回覆不明只核對原單，不重做另一張。重開、配對失效、儲存不足、損壞輸入、過時價格與其他視窗的新單均沿用 F11 的保留與隔離原則。

## M14：備份與真正舊版保護

選項原始來源、行識別、款項與成本關聯須完整備份、還原與跨儲存搬移。新資料需要獨立 restaurant-menu-v1 寫入保護與相應新格式；真正的0ba40cfb舊寫入者須在改動資料前停止。同一支舊程式仍須通過既有全額／分次流程正控制。不能只加一個舊版不認識但會忽略的欄位。

使用選項設定或保存過選項原單後，復原保護格式至少為7。完整檔案即使重新計算內容摘要，也不能把選項資料標成格式6；瀏覽器及原生往返後保留設定來源與舊原單，新的報價使用還原後的新世代。未知格式仍須拒絕。

保存過公開選項顧客原單後，另要求 restaurant-public-menu-v1 及至少格式8，SQLite 明確保存 customer_menu。只認識 M6 選項格式7的真實舊程式必須在寫入之前停止，避免還原時丟失顧客的選項來源。完整備份產生與讀取兩端，都拒絕改成格式6／7或移除新特徵的檔案，即使內容摘要重新計算亦同；合法格式7的店主選項原單仍保持支援。

## M15：拒絕猜測與偽造

驗證原生／HTTPS 操作者、明確型別、精度、數量、結構、未知／重複選項、群組界限、價格、原料、店面、復原版本與報價。未完成接線的選項命令不得被當成普通餐點成功保存。規則在正式服務，不以隱藏按鈕作為安全邊界。

## M16：完整驗收與範圍

固定同一份丼飯／飲料／原料情境，先量測真正的0ba40cfb缺口，再驗證同商品不同選項、精度、整車共料、零元／負價、少飯／移除、套餐、價格與配方變更、部分到全額取消、混合收款、FIFO、廚房、桌碼、Agent、備份往返、真正舊版、晚期回滾與原編號復原。實際 UI→adapter→保存→回覆→重開、認證 IPC／HTTPS、成本帳啟用／未啟用均須覆蓋。純試算或本機來源不代表實體設備、真人、正式資安、外送平台、新安裝檔或完整 ERP 已完成。

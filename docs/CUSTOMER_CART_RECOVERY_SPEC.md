# 未送出的點餐自動保存

開發分支；既有安裝檔尚未包含。所有店家、全部功能免費。

## D1 正常操作

選餐、未選完的份量／加料、姓名、桌號文字與備註自動保留原始輸入；取消確認畫面不刪除內容。重開同一瀏覽器、同一點餐網址後接回，送出前重新核對價格及可用量。保存草稿不建立訂單、不預留庫存、不收款。

## D2 同一份草稿

同一瀏覽器來源同時只有一個顧客頁編輯與送單。另一個分頁顯示等待；原頁離開後自動接手。IndexedDB 交易驗證 owner／fence，適用於一般區網 HTTP，不能假設 Web Locks 或 crypto.randomUUID 可用。輸入先同步保存於各寫入者獨立的原始暫存，再交給 IndexedDB 核對，避免輸入後立即重開而尚未完成非同步保存。

離開時同步留下原 owner／fence 的釋放提示，避免卸載取消非同步交易而每次都等租約到期。提示只允許嘗試接手，最後仍須 IndexedDB 交易換發 fence；舊提示不能釋放新 owner，舊寫入仍被拒絕。

頁面凍結前也必須保留暫存並中止尚未完成的本地交易；不再排入需要凍結頁面回呼的釋放交易，避免它占住 IndexedDB 而讓另一分頁無法接手。解凍後重新取得 writer，舊報價與送單回覆不能更新新畫面。

原始暫存僅含公開餐點快照與顧客填寫內容；不能存桌碼金鑰、追蹤憑證、價格核准 token 或私有店面資料。暫存不能授權價格或寫入帳本。依店面資料庫回傳的 opaque scope 區分店面、正式還原世代、桌碼及菜單模式。不同 scope 保留原資料，不互相帶入。

## D3 正式原單

同一 IndexedDB writer 交易內才可建立／更新原有顧客送單 journal。新請求沿用草稿文件編號；結果不明時保留原始 request、quote、context 與草稿證明，先核對原單。正式 request JSON 與帳本格式維持既有協議。

核對實際原單及金額後，僅清除文件編號與原始意圖證明均相同的草稿。較新的輸入、另一桌或另一世代的草稿不能被舊回覆清掉。失去 writer 的非同步報價、送單及確認回覆不得覆蓋接手分頁。舊 journal 缺少草稿證明時不推定它對應目前草稿。

送出中不能按「取消」誤以為撤回訂單。結果尚未核對時，「返回菜單」只離開確認畫面；重新開啟仍顯示原單內容與原金額，不重新套用店家後來修改的價格。

## D4 異常處理

儲存空間不足時保留當前輸入及上一份紀錄，提示重試／下載；未保存的新意圖不能送出。損壞資料保留供下載，使用者明確選擇後才清除這張未送出的草稿。較舊寫入者的不同內容保留為可下載來源，不自動蓋過最新版本。

## D5 驗收範圍

實際非安全 HTTP 與固定憑證 TLS，普通與選項餐點、立即重開及真正新視窗、未選完的餐點、原始空白／換行、兩個實際同來源分頁、真實 pagehide 接手、scope／桌碼／還原世代變更、改價再次確認、送出後回覆遺失、舊回覆、暫存或 IndexedDB 空間不足、損壞資料下載／清除及完整帳本核對。四語、兩種外觀、360px 觸控畫面須實測。

瀏覽器草稿不等於跨裝置雲端同步；正式訂單及庫存仍由店面資料庫共用。實體手機、斷電、印表機、人類可理解性、長時間營業及完整 ERP 所有原始能力仍各自待驗收。

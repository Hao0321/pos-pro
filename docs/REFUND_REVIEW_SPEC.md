# 三步退貨與精確退款

狀態：開發中；完整 ERP 原始 31 項目標及庫存成本 I1–I12 保持原範圍。此處處理 POS 原單退貨，預訂取消仍走原預訂流程，不冒充外部刷卡平台的自動退款。

## RF1 找到原單，填退回數量

簡易首頁提供「退貨、退款」入口，店主可找會員及非會員的 POS 原單；不必先建立會員。保留原單號、時間與商品原文，超過顯示頁數仍可查。已退完、非 POS 來源與預訂餐飲原單清楚分流，不讓店主錯把已耗用原料回庫。

輸入保留原始文字，支援千分之一數量。空白表示未選，明確 0 不退；負數、超額、非有限、指數與過多小數均提示，不截成整數、不猜成 0、不默默夾到上限。大輸入框、可達的大按鈕，詳細計算預設收起。

## RF2 相同計算，明確退款方式

原生與瀏覽器共用唯一純退款模型。以整數分、整數千分數量、BigInt 比例及明確四捨五入計算累計應退，再扣已實退；最後一次退回恰好結清原金額。原始價格乘數量的比例權重保持完整，到最終財務分才取捨；各付款方式本次不會倒扣已退款，尾差在剩餘原付款額內分配。現金、刷卡、儲值、點數、折讓都依原保存資料，不依今天價格或新增金流。過去已保存的退款不重算、不改寫。

畫面依同一份權威預覽顯示「這次退回」及必要的現金、原刷卡款、儲值、實際點數調整。刷卡工具的實際退款仍由店主在原工具完成，本系統保存記錄，不能誤導為已呼叫金流平台。折抵與分攤細節折疊。

## RF3 核對後才保存

店主按「看退款」取得目前權威資料的預覽；新確認帶版本化 `pos-refund-review/v1`，固定店面、還原 epoch、原單、累計退款、會員狀態、開班、選項與金額摘要的雜湊及時間。新提交必須在同一個實際原子交易重新核對，資料／金額變更拒絕並保留輸入，重新預覽，不自動換金額後過帳。

預覽不授予權限，不能包含角色、憑證或任意寫入。實際目前店主帳號須匹配；IPC、HTTPS 與獨立瀏覽器都維持權威邊界。原單已保存時先找原結果，再檢查新操作時效與預覽，過期預覽不妨礙相同原單找回；同編號改內容仍拒絕。未帶新預覽的舊內部合法請求保留原相容語意，不冒稱已人工核對。

## RF4 只清掉完整回覆

新退款簽章條件式包含整份已核對預覽；舊請求沒有此欄位時，原簽章維持。呼叫端核對原退款編號、原單、商品數量、凍結金額、原付款分配及必要成本回執，才能清掉財務暫存。提交後回覆遺失、回覆被截斷、重啟與找回均沿用同一份原請求，不重新付款、不再回庫。

## RF5 草稿接續與舊單改動

草稿按店面、目前帳號／角色及原單隔離，保留原數量文字、原因、已核對預覽和不明原請求。編輯、其他裝置退貨／會員變更、還原或來源改變會使預覽需要重新核對。未保存可離開再回來；正在提交或結果不明不能以關閉表單或換編號消除原單。不明退款重新開啟時直接回到原退貨頁，提供「核對上次退貨」及正式復原入口。

空間不足或損壞保留原文，提供保存重試／下載支援草稿，不宣稱完成保存或可跨格式自動匯入。確認後只清除相符的原草稿，不能清掉另一張單。

## RF6 多語與驗證

繁中、英文、日文、簡中，明亮／海報與 360px 均需實際可操作；新增說明及錯誤加入共用翻譯。無真人無提示驗收前，不宣稱老人或小孩已通過。

先保存舊版實際原生來源、相同原請求與原始輸入，證明舊 UI 截斷小數／顯示值不符，並以已知半分正負控制校準金額。候選覆蓋零價、半分、混合支付、儲值點數、累計部分到完整退回、舊已退尾差、大數邊界、原生／瀏覽器實際持久化、兩個 HTTPS 客戶端、原單回覆遺失、晚期回滾、配額、過期／店面／角色與畸形回覆。完整成本帳、備份、原編號復原及最終同來源建置／回歸一併保留。精確新安裝檔、實體設備、真人、正式財稅／資安及完整 ERP 仍未因此完成。

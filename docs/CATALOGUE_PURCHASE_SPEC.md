# 公開價目目錄直接準備採購

## C1. 使用流程

在原有「Agent 幫我建單」貼上、選檔或拖入 `business-catalogue/v1`。店主直接選品項及數量，系統用原參考單價試算；下一步接續既有商品對照、供應商、日期與採購確認。選品不會保存採購、收貨、付款或把資料送給供應商。畫面使用四種語言、兩種風格與至少 48px 控制，自訂數量保留原字串。

## C2. 文件與身份

`business-catalogue-order/v1` 是買方依公開目錄準備的草稿，不是供應商的報價或已接單證明。它含固定的 `id`、`createdAt`、`recipientStoreId`、完整原 `catalogue` 和明確選取的 `items: [{sku, qty}]`。同一目錄可以在另一次明確新建時準備另一張單；同一草稿編號改數量、價格或來源不能變成第二張採購。

原目錄的 revision 必須符合原公開內容的 SHA-256；它辨識內容，不認證公司身份。SKU 屬於目錄來源公司。與本店 ID 恰好相同不能自動配對；沿用已核對的公司品項對照，或請店主核對。未知商品、單位差異及未確認的供應商不能猜測。

## C3. 數字

選取數量使用一般小數，最多三位；單價保留新台幣分。小計沿用既有採購分毫計算，再加總整數分。空白／零表示未選取；未完成、超出精度、負數、重複 SKU、溢位與不支援幣別阻擋下一步。不得把未知數值補零或把售價改成本店售價。

## C4. 保存與原單

正式確認前固定草稿 ID。採購與 `procurement.sourceCatalogue` 一起原子保存；來源包含完整目錄、選品與本店商品映射。回覆遺失或重新匯入同一原草稿時先查原紀錄。比較完整來源與保存條件，不靠目前商品或單據外觀猜測。確認後的來源、審批、後續收貨與完整備份都保留。

## C5. 變更與隔離

店面、帳號、還原世代及其他視窗沿用私人草稿隔離。方案原輸入在斷線、容量不足及核對失敗時保留。商品單位、名稱、對照或來源在核對到寫入之間變動，先要求重新核對；不寫入錯誤商品。配對手機共用正式資料，不建立離線副本。

## C6. 相容保護

新服務透過 Agent context 明示支援。使用此來源後，採購文件格式3、瀏覽器記錄格式2及 SQLite feature fence 保護較舊讀寫器，避免忽略或移除來源。完整備份、跨儲存還原與歷史來源都攜帶 `catalogue-purchase-v1` 標記；未使用的舊資料不強制轉版。通用設定不能偽造或移除保護。Recovery graph 本身的結構未改變，沿用既有版本與原始 JSON 保存方式。

## C7. 驗收

先保留舊版本實際拒絕目錄、且未寫入任何採購／庫存／款項的基準。驗證直接選品、自動分毫試算、供應商範圍 SKU、未知對照、原編號、真正回覆遺失、重匯原草稿、冷啟動、容量不足、寫入後例外、實際收貨、審批及完整備份。桌面、HTTPS配對及獨立瀏覽器都必須用正式路徑；用真正上一版證明拒絕新資料讀寫。

## C8. 完成範圍

這一條流程不證明外部 Agent 實際互通、供應商接單、真人老人／孩童易用性、實體裝置或整套 ERP 完成。39項業務義務、至少45項能力與正式資安缺口繼續保留。M24–M33維持凍結；本流程驗收後更新既有草稿PR並收尾。

# 跨公司 Agent 單據交換：設計與採用理由

## 為什麼值得使用

對方公司保留自己的軟體與 Agent，只要輸出公開 JSON 格式；收件方能匯入、核對與建單，減少重新打字。使用本 ERP 的價值是免費取得從單據到庫存、出餐、付款與帳務的可追溯流程，以及不確定時保留原編號的復原能力。資料、對照與完整備份可匯出，不以格式封鎖作為採用理由。

## 兩層協議

- **`business-document/v1`**：可攜交換草稿。包含來源公司代碼、外部單號、產生時間、單據用途、幣別、品項代碼／條碼／名稱、數量、單位、單價及合計。對方不必取得本店密碼、庫存或員工資料。若知道收件店面 ID，可明確指定並防止送錯店。
- **`pos-document-draft/v1`**：本店核對後的建單草稿。帶入本店 ID、當下品項版本及角色限制；最後使用既有交易機制提交。

這兩份都是本專案公開的 v1 規格，不宣稱已成為業界通行標準。欄位與訂購／回覆概念參考 [OASIS UBL 2.4](https://docs.oasis-open.org/ubl/os-UBL-2.4/UBL-2.4.html) 及 [Peppol BIS Ordering](https://docs.peppol.eu/poacc/upgrade-3/profiles/28-ordering/)。目前沒有 UBL XML／Peppol 網路、電子發票或合規認證。

## 使用者看到的流程

1. 匯入 JSON 檔、拖入單據，或由 Agent 連結直接打開草稿。
2. 品項能辨識就直接顯示；不確定時，只問「這是店內哪個商品？」。管理員可選擇記住這家公司的品項對照，同店面各裝置及完整備份共用。
3. 顯示來源、品項、數量與總額；補上必要交付資料後按一次建單。單據完成時顯示清楚成功訊息，原先的重試錯誤必須消失。

銷售用途目前是帶入未收款購物車，預訂用途會正式預留資源，採購用途會正式建立採購單。收款、入庫、付款及退款各自保留明確操作。

## 對照與核對規則

- 同一來源公司可保留外部品項代碼到本店商品的對照；第一次由管理員核對，後續可自動套用。
- 沒有對照時依已存在的品項代碼、條碼、唯一完整名稱辨識；多義或未知品項不猜測、不偷偷建立新品。
- 單位須與本店相同，不做隱藏的公斤／個數換算。銷售價須與本店一致，外部合計須等於明細；採購單價只在管理員採購流程採用。
- 本版僅接受 TWD。擴充多幣別、稅額、折扣、退貨、收貨及請款等交換類型時，要以新 profile 明確定義，不讓未知單據冒充訂單。
- 來源公司代碼是對照鍵，不是身份認證或電子簽章。公開協議不增加匿名寫入權限，未知欄位與執行指令會被拒絕。
- 來源公司代碼與外部單號決定固定建單 ID；相同單據重送不重建，內容改變時不得沿用同一單號冒充原單。Agent 應保存原始 `createdAt`，不可在重試時改時間。

## 接軌與可攜性

規格、schema 和閱讀指南隨原始碼以 MIT 提供，其他系統可自行實作 adapter。一般化協議不強迫對方換 ERP，也不代表所有第三方 Agent 已完成互通驗收。本版驗證的是本實作的 JSON 導入與既有交易鏈；不同公司的真實 Agent、既有 ERP 與大型單據仍需各自驗收。

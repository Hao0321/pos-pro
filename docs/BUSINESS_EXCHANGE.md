# 跨公司 Agent 單據交換：設計與採用理由

## 為什麼值得使用

對方公司保留自己的軟體與 Agent，只要輸出公開 JSON 格式；收件方能匯入、核對與建單，減少重新打字。使用本 ERP 的價值是免費取得從單據到庫存、出餐、付款與帳務的可追溯流程，以及不確定時保留原編號的復原能力。資料、對照與完整備份可匯出，不以格式封鎖作為採用理由。

## 兩層協議

- **`business-document/v1`**：可攜交換草稿。包含來源公司代碼、外部單號、產生時間、單據用途、幣別、品項代碼／條碼／名稱、數量、單位、單價及合計。對方不必取得本店密碼、庫存或員工資料。若知道收件店面 ID，可明確指定並防止送錯店。
- **`pos-document-draft/v1`**：本店核對後的建單草稿。帶入本店 ID、當下品項版本及角色限制；最後使用既有交易機制提交。

這兩份都是本專案公開的 v1 規格，不宣稱已成為業界通行標準。欄位與訂購／回覆概念參考 [OASIS UBL 2.4](https://docs.oasis-open.org/ubl/os-UBL-2.4/UBL-2.4.html) 及 [Peppol BIS Ordering](https://docs.peppol.eu/poacc/upgrade-3/profiles/28-ordering/)。目前沒有 UBL XML／Peppol 網路、電子發票或合規認證。

## 使用者看到的流程

2.9.0 可從「快速建單」一鍵複製建單說明、角色範圍內的店內資料及範例給自己的 Agent，無須先找 schema 或手工組資料包。貼回時可接受單一 JSON 程式碼區塊；內容驗證不放寬。詳見[簡易工作台](EASY_WORKSPACE.md)。

1. 匯入 JSON 檔、拖入單據，或由 Agent 連結直接打開草稿。
2. 品項能辨識就直接顯示；不確定時，只問「這是店內哪個商品？」。管理員可選擇記住這家公司的品項對照，同店面各裝置及完整備份共用。
3. 顯示來源、品項、數量與總額；補上必要交付資料後按一次建單。單據完成時顯示清楚成功訊息，原先的重試錯誤必須消失。

銷售用途目前是帶入未收款購物車，預訂用途會正式預留資源，採購用途會正式建立採購單。收款、入庫、付款及退款各自保留明確操作。

## 對照與核對規則

- 同一來源公司可保留外部品項代碼到本店商品的對照；第一次由管理員核對，後續可自動套用。
- 沒有對照時依已存在的品項代碼、條碼、唯一完整名稱辨識；多義或未知品項不猜測、不偷偷建立新品。
- 單位須與本店相同，不做隱藏的公斤／個數換算。銷售價須與本店一致，外部合計須等於明細；採購單價只在管理員採購流程採用。
- 本版僅接受 TWD。擴充多幣別、稅額、折扣、退貨、收貨及請款等交換類型時，要以新 profile 明確定義，不讓未知單據冒充訂單。
- 來源公司代碼是對照鍵，不是身份認證或電子簽章。公開協議不增加匿名寫入權限，未知欄位與執行指令會被拒絕。
- 來源公司代碼與外部單號決定固定建單 ID；相同單據重送不重建，內容改變時不得沿用同一單號冒充原單。Agent 應保存原始 `createdAt`，不可在重試時改時間。

## 接軌與可攜性

規格、schema 和閱讀指南隨原始碼以 MIT 提供，其他系統可自行實作 adapter。一般化協議不強迫對方換 ERP，也不代表所有第三方 Agent 已完成互通驗收。本版驗證的是本實作的 JSON 導入與既有交易鏈；不同公司的真實 Agent、既有 ERP 與大型單據仍需各自驗收。

## 供應商採用、交付與不同客戶的價格（後續設計，尚未實作）

產品要先證明供應商少重打、少接錯規格、能追蹤買方是否確認，不能把「支持我們的協議」當成採用誘因。用真實供應商驗證首次回覆時間、重複訂購時間、品項／價格錯誤與是否願意再次使用；不從軟體測試推定市場採用。

保留三條入口：已會輸出公開 JSON 的 ERP／Agent 直接交換；沒有系統的供應商使用免安裝的專屬詢價頁；完全不配合的供應商繼續給原來的 Excel、PDF 或文字，由買方整理成草稿再核對。**本版實作只有 JSON／Agent 草稿導入，沒有 Excel／PDF 訂單辨識或跨公司供應商網頁。**未來辨識不明的規格、單位、稅價仍須顯示來源並由人確認，不能猜成已同意條件。

預定操作鏈：店家選供應商與品項 → 傳「詢價／下單」文件或專用連結 → 供應商確認數量、單價與交期 → 店家看到合計與差異，確認後建立採購單 → 回覆確認號給供應商。既有議定價格才可直接下單；沒談定價格時只送詢價。接收報價不能直接代表雙方成交，也不能直接入庫或付款；數量或價格更動需產生新修訂、重新確認，保留原版。

首階段可由人透過原有 LINE／Email 傳檔，或讓店家下載後匯入；這不等於本系統已串接 LINE／Email。後續安全連結需要獨立的跨公司收件服務與部署驗證，不能把現有私人區網配對網址當成外部供應商入口，也不能把可轉傳連結當成供應商身份證明。查看報價與確認交易的權限要分開；專屬價格需要驗證收件方，連結可過期、撤銷並防重送。軟體功能免費的原則不變，公共代管的運算、容量與濫用防護仍須有明確成本與運作方案。

### 價格屬於交易條件

專屬價格以賣方、買方、商品規格、報價單位與計價基數、數量級距、幣別、含／未稅、運費／折扣、有效期間及報價修訂共同決定。例：同款雞腿肉每公斤，一般價 200 元、甲店合約價 180 元、乙店合約價 170 元；哪個合約可以用整批數量價，須由規則明訂，不以「最低價」任意覆蓋已議定條件。無法得到唯一適用價格時，要求供應商確認。

優先採用雙方確認且有效的單次報價，其次是符合條件的合約／客戶價，再依明確規則使用級距或一般價。客戶分級不允許買方或 Agent 自報；客戶身份與可用價表由供應商端驗證。數量、交期或規格變動時重新核價，不沿用失效條件。正式訂單保留已確認的單價、稅費、運費、折扣、數量與版本快照；之後改價表不能更改歷史單據。

對外只輸出該收件人可用的本張詢價／報價明細。甲店不能讀到乙店價、供應商底價或成本；另一家公司 Agent 也不能取得整份客戶價表。本版「給自己的 Agent」資料包依操作者權限可能含內部商品成本、供應商資料，**不是對外詢價文件，不應轉傳給供應商或顧客**。對外專用輸出須另定最小欄位及權限。

新的客戶專屬報價 profile 必須要求收件方、發件方、外部單號、修訂、效期、引用的詢價／訂單與明確計價條件；v1 的可選收件方與來源代碼不補足身份驗證。不能默默把這些欄位加進拒絕未知欄位的舊版 schema。接單、確認、出貨、收貨、請款與付款仍各有獨立狀態和原單號。

訂單／訂單回覆與價目目錄分開建模，可參考 [Peppol Ordering](https://docs.peppol.eu/poacc/upgrade-3/profiles/28-ordering/)及 [Catalogue With Response](https://docs.peppol.eu/poacc/upgrade-3/profiles/1-catalogueonly/)；這是設計參考，沒有 Peppol 網路整合或合規認證。

必要驗收包括：甲店無法取得乙店報價、轉傳／偽造身份不能確認交易、箱／公斤與含稅差異不能混算、過期或改量重新確認、改價不改歷史、版本衝突、同單重送、收件斷線後以原單號恢復，以及不懂 JSON 的真人能完成首次與第二次訂購。

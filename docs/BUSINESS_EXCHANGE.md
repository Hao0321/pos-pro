# 報價與 Agent 建單：從公開價目表到採購

2.12.0 提供公開商品目錄、指定收件人的報價、各客戶參考單價、報價修訂，以及收到報價後核對建採購。所有店家、全部功能免費；對方可以用自己的 ERP 或 Agent 產生格式，不必改用 POS Pro。

## 第一次怎麼用

**買方**到「報價與價目表」，按「複製我的店面資料」，透過原來使用的通訊方式交給供應商。這張資料卡只有店面代碼和店名。

**賣方**搜尋「報價」進入畫面：

1. 貼上買方的店面資料卡，或填收件店面代碼與名稱；第二次可直接選之前的客戶。
2. 點商品、填數量和這位客戶的單價。可勾選記住單價，下次帶入後仍要核對。
3. 選到期日，確認單價已含本單全部費用，保存後複製或下載，自己傳給對方。

**買方**把報價貼進「快速建單」或匯入 JSON 檔，核對商品對照、供應商、日期與金額，再按確認建立採購。沒有對照的品項先問清楚，不猜商品或換算單位。單據不代表已收貨或付款。

報價的商品代碼屬於賣方；即使剛好和本店另一商品的 ID 相同，也不視為同一商品。先使用這家供應商已確認的對照，否則依唯一完整名稱提出對照；無法辨識時由人選擇，再按來源公司記住對照。

沒有 POS Pro 的供應商可依公開 schema 讓自己的 Agent 輸出 business-quote/v1。本版沒有代替對方操作其他 ERP，也沒有 Excel／PDF 訂單辨識、跨公司代管報價頁或 LINE／Email 自動傳送。

## 公開價格與客戶價格

「選商品、下載價目表」只輸出勾選商品的代碼、名稱、單位及一般售價，以及本店代碼、名稱、產生時間與內容版本。**不包含成本、精確庫存、配方、供應商清單或客戶價表**。一般價格是參考，不能直接代表雙方已同意數量、交期或附加條件。

已啟動的顧客點餐伺服器另提供 GET /api/catalogue，只列目前顧客菜單已開放的商品（有庫存且售價大於零）。它不會自動建立對外通道。GET /.well-known/pos-business-exchange 提供格式探索入口，/agent/manifest.json、/agent/*.schema.json 與 /llms.txt 可讓對方 Agent 閱讀。手動下載的目錄可包含店家明確勾選的缺貨或零元商品。

報價以**收件店面代碼**區分客戶。甲店 180 元、乙店 170 元可以各自保存；單張對外報價只有該收件人的明細，不會帶出整份客戶價表。記住的單價是再次報價時的輸入參考，每張仍需賣方核對；它不是自動生效的合約或最低價保證。

v1 報價只接受 **TWD、單價已含本單全部費用**，合計依每列數量乘單價取到分後加總。沒有額外稅額、運費、折扣欄位，不做隱藏的稅費、幣別或單位換算。若還要加運費、價外稅或改包裝單位，應先取得符合實際條件的新報價；本版不支援把這些條件偷偷加進未知欄位。介面語言切換不會換匯。

## 公開格式與可攜性

| 格式 | 用途 | 主要限制 |
| --- | --- | --- |
| business-party/v1 | 提供店面代碼與名稱 | 資料卡不驗證身份 |
| business-catalogue/v1 | 公開參考價格目錄 | 不是訂單或報價承諾 |
| business-quote/v1 | 指定收件人的報價 | 必填收件人、修訂、效期與明確計價條件 |
| business-document/v1 | 可攜銷售、預訂、採購草稿 | 保留原有嚴格欄位；不混入新報價欄位 |

本店核對後使用 pos-document-draft/v1 及既有正式交易介面。舊協議的 schema 沒有放寬未知欄位。公開格式以 MIT 隨原始碼提供，其他 ERP 可自行實作 adapter；這不是 UBL／Peppol 認證。原設計比較曾參考 [Peppol Ordering](https://docs.peppol.eu/poacc/upgrade-3/profiles/28-ordering/) 與 [Catalogue With Response](https://docs.peppol.eu/poacc/upgrade-3/profiles/1-catalogueonly/)，未整合其網路。

## 保存、修訂與斷線

保存報價前先在裝置留下操作編號。原生提交已完成但回覆遺失時，畫面保留待確認狀態；重新開啟會接回報價確認頁，沿用原編號查回原版本。確認保存前不顯示已保存，也不讓待確認操作直接變成新報價。

修訂使用原報價 ID、新的操作 ID 及遞增版號。舊版、原價格、原收件人及原建立時間保留；不能把修訂改寄另一間店。其他裝置已更新版本時，舊版本提交會要求重新核對。

買方以「賣方代碼＋報價 ID＋收件店面」決定固定採購操作身份，各修訂共用同一身份。已確認建立後，另一修訂不能另外生出一張採購或覆蓋原單；即使換操作編號，同一報價家族也不能重建。正式採購保存報價全文及本店商品對照，後續調價不改歷史，也不覆寫買方零售價。

首次建立必須在報價效期內。已成功建立的原編號重試，可以在效期後查回原結果；尚未提交成功的過期報價不能靠重試補建。報價時間須有明確時區，支援到毫秒；不能從本地時區猜測到期時間。

未送出的報價表單依店面及使用者保存在裝置草稿中，切換語言、風格和重新載入會保留輸入。正式報價、各客戶價格和回執存於共用店面資料庫，隨完整備份保存與驗證。手機使用同一台電腦的私人 HTTPS 資料來源，斷線不另建離線副本。

## 權限與邊界

只有已登入管理員能管理報價、客戶參考價格及讀取完整歷史；桌面 IPC 與配對手機在伺服器端檢查身份。一般稽核紀錄寫入介面不能建立報價回執。公開目錄不提供匿名寫入或取得私人報價的 API。

**公司代碼與店面資料卡不是身份認證、電子簽章或加密。** 檔案仍可被轉傳或修改；收件代碼只能避免正常匯入時送錯店，不能防止別人閱讀已拿到的檔案。請透過雙方確認的管道傳遞並核對報價來源。本版不宣稱可撤銷已傳出的檔案、證明供應商法律身份，或自動證明成交。

傳遞檔案後，賣方畫面不會自動知道買方是否接受，也沒有跨公司簽收、出貨追蹤或自動訂單回覆。這些仍需獨立的身份、授權、傳輸與服務部署驗證，不能把私人區網配對網址當作外部供應商入口。

目前每張報價上限 100 品項、32 KB，數量最多三位小數、單價最多兩位，效期最長 366 天。店面報價歷史上限 8 MiB／10,000 次修訂，客戶參考價最多 2,000 位、每位 1,000 組商品單位；到達限制會停止新增並保留原資料，不會自動刪舊報價。大規模封存、多幣別、價外稅、運費、數量級距、合約價與客戶身分服務仍待實作。

## 為什麼供應商值得試

先前的品項與客戶單價可以再次帶入，原版與改價有紀錄，買方能直接核對建單，減少重打與傳錯價格的機會。格式公開，對方可以繼續用原來的軟體；採用理由應是少做事、少出錯，而不是被格式綁住。

自動化測試驗證本實作的資料隔離、重送、復原、桌面及配對 Chromium 流程。真實供應商是否願意使用、獨立公司的 Agent 是否順利互通，以及長者與首次使用者能否無提示操作，都仍需要真人與外部環境驗收，不能從測試數量推定。

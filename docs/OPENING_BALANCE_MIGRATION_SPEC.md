# 原單帳款搬家與後續收付款

狀態：M17m 開發中。這份規格不是功能完成、上線或完整 ERP 認證。

## OB1 讓使用者少做事

沿用「交資料 → 看結果 → 確認」的搬家入口。同一份來源內的主檔、庫存、未收、未付與貸項必須一起核對。系統先整理已知資料，只詢問缺少或有衝突的事實。未支援的內容要連同原檔保留並阻擋整批保存，不能顯示成功後漏掉餘額。Agent 只準備資料；本店目前的店主確認才是寫入授權。

完成的判準包含搬家後的使用：原單能在既有客戶收款／供應商付款流程中抵付、解除抵付、退回及更正。另做一份無法收付款的欠款清單，不算完成。

## OB2 搬剩下的金額，不重播舊生意

每張原單保留來源系統、來源公司、資料種類、原編號、往來對象原編號、單號、單據日、到期日、幣別、發票或貸項種類及切換日的未結清金額。原單總額與以前已付的金額可供核對，但不建立新的歷史收付款。正負號與單據種類必須一致；空白不是零。所有金額由十進位原文字轉成整數分，不經浮點乘除後猜測。

目前本地帳本使用 TWD；外幣資料需要換匯、控制科目及原幣餘額的完整規則，尚未驗收前不能自動當作台幣。跨幣、銀行／現金、預收付、儲值／點數、資產、完整歷史與其他 ERP 領域仍是完整目標的必要工作。

ERPNext 的官方工具以原單與未結清餘額搬入應收付，並要求切換日與原報表核對；原總額、先前付款與未結清額應分清楚。[Import Outstanding Invoices](https://docs.frappe.io/erpnext/opening-invoice-creation-tool)

## OB3 身份與原始資料

來源鍵由來源系統、公司、種類與原編號組成，不使用列號或名稱代替身份。不同來源編號指向同一經濟單據時，必須處理重複，不能再加一次欠款。同名只能成為待確認候選。會員與法律／商務往來客戶是不同身份；不能因為姓名相同就合併。

原 JSON／CSV／工作簿與來源列位置要持續保留。欄位解碼、人工補充、身份選擇、試算與回執可重算。已知的數字或日期不能被「修復」成零或另一個數字。新的解碼規則不得改寫已保存舊版本回執的意義。

## OB4 共同收付款權限

期初發票是獨立原單請款，不偽造成今日的銷售交付或採購入庫。既有客戶／供應商款項帳依明確原單引用分配款項。

期初貸項是有來源的可抵付餘額，不能偽造成銀行收款／預付款。貸項可抵付同一對象的新舊請款；解除抵付仍回到原貸項。實際退款必須選現金或銀行並確認實際發生；現金仍受目前班次約束。貸項不可用一般收付款沖銷動作刪掉來源。

帳款上下文在各自款項帳的確切版本邊界生效。重播舊歷史時只能看到當時已搬入的原單與貸項，不能把後來的貸項提前供舊操作使用。新操作須帶入核對時的上下文摘要；伺服器重算身份、可用款、原單與版本，不接受 Agent 自稱核准。

## OB5 分錄與對帳

| 來源 | 借方 | 貸方 |
| --- | --- | --- |
| 未收發票 | 1141 應收 | 3902 期初待核對 |
| 客戶貸項 | 3902 期初待核對 | 1141 應收 |
| 未付發票 | 3902 期初待核對 | 2101 應付 |
| 供應商貸項 | 2101 應付 | 3902 期初待核對 |

沒有新的營收、進貨費用、稅、現金或庫存異動。貸項抵付同一控制科目的發票不新增總帳金額；客戶貸項退款借應收／貸實際款項，供應商貸項退款借實際款項／貸應付。一般預收付沿用 2192／1261 的既有規則。

按對象、幣別、單據種類、單數與到期日核對，另接受原報表的獨立合計。庫存、應收與應付各有自己的控制科目，不得再從期初總帳匯入相同餘額。3902 的差異必須追查來源，不能塞進保留盈餘或四捨五入而宣稱已平帳。[ERPNext Opening Balance](https://docs.frappe.io/erpnext/opening-balance)

## OB6 保存、還原與更正

主檔、庫存、帳款、權限邊界、回執與版本旗標同一交易提交；任何後段失敗整批回滾。瀏覽器使用同一筆受保護帳本寫入。失去回覆後先查原編號，不再建立另一張原單。備份需包含完整原單來源與校驗資料；真正前一版本的讀取與寫入都要實測拒絕不懂的新帳本。

未使用的錯誤批次只能透過保留歷史的受控撤回／替換；已收付款或消耗庫存後須使用連結原單的更正，不刪除歷史或回復整間店的舊備份。這些流程也是驗收範圍。

## OB7 驗收與現況

原生 SQLite、瀏覽器、手機共用店面路徑都需執行實際操作；涵蓋新舊請款混合抵付、部分款、貸項、退款、更正、跨版本歷史、生效邊界、錯誤角色、換店、同編號不同內容、重複來源、少一分／多一分、後段回滾、額度不足、失去回覆重啟、備份與真正前版拒讀拒寫。

本輪先建立原單來源解析與共同款項帳的版本化上下文。正式保存入口、完整組合搬家、撤回／更正、操作畫面與裝置驗收仍需逐項完成。現有嚴格 Cleanup 的 6 個 REVIEW／3 個 NOT_CHECKED 保留開啟；原始碼開發進度不等於發佈資格。完整 32 項 ERP 義務與至少 38 項能力範圍維持不變。

M17m-B.1 補上內部的整份來源核對規劃。相同原始文字可一起解析主檔、庫存、未收、未付與貸項；沿用既有主檔身分與庫存保管檢查，不把展開的工作簿再序列化通過 Agent 檔案大小限制。原報表合計分成庫存價值、未收發票、客戶貸項、未付發票與供應商貸項五項；沒有提供時顯示未核對，正負兩邊互相抵消的錯誤也會各自阻擋。控制科目試算只含 1211、1141、2101、3902，沒有重播舊生意或舊現金。

核對規劃中的同名與同電話只列候選，須明確選擇既有對象或另外建立；既有選擇綁定目前名稱，來源永久對照不能改指另一個人。來源有未收單引用的客戶主檔投影為財務往來客戶，使用獨立身分，不因會員同名就合併；未被未收單引用的會員主檔仍保留原會員工作。生日、儲值、點數等尚未處理的內容會阻擋整批核對，不能從財務主檔略過。既有往來資料先保留本店內容，原值與來源值並列；這項規劃不會自動覆寫聯絡資料。供應商的商品與未付單使用同一個主檔選擇。有內容的未處理欄位仍阻擋；原檔已指定的編號欄另保留來源證據，不把它誤判為遺漏欄位。

上述規劃的 `factsReady` 只代表這一層事實核對通過，`writeAvailable` 固定為 `false`。它沒有 IPC、HTTP、瀏覽器保存入口或持久化回執；既有公開寫入權限也拒絕這個新規劃協議。庫存成本完整保存後影像、整批原子提交、原編號恢復、受控更正、實際畫面、共用手機與新格式14拒讀／拒寫仍未完成。原始碼驗證包含真正 SQLite 匯出、實際建立往來客戶後的候選與舊核對失效，以及真正前版的正反控制；不把唯讀規劃稱作已搬家成功。

目前的上下文是內部試算資料，沒有新增可由 Agent、IPC、HTTP 或瀏覽器直接提供上下文的保存入口，也沒有提升持久化格式。共同帳本會由原始文字重建金額與身份；公開款項 API 拒絕呼叫者夾帶上下文。帶有尚未處理的商品、庫存、歷史、儲值或無關主檔時，這個金融核心上下文也不能冒充完整搬家。真正前一版讀寫現有格式仍須相容；未來啟用保存功能時，需另驗收新格式的拒讀／拒寫，不能沿用這個相容測試宣稱已通過。

相容性補強：欄位缺席與明確填入 `null` 不相同。沒有生效的帳款來源時，新請求不能保存 `expectedOpeningDigest`，包括空值；否則較舊的嚴格讀取器會遇到不認識的欄位。前一個開發版本已接受的空值歷史請求，仍按原內容讀取與核對原回執，不刪改輸入。這項歷史相容只適用於當時沒有生效來源的紀錄；不能拿空值核准已有來源，或把新的來源倒填到舊款項之前。驗收使用前一版真正 API 產生的資料庫與保留的原始回執。

已含空值的既有歷史，仍需使用認得該欄位的版本讀取；補強不會改寫原請求來假造更早版本的相容性。新請求則在沒有來源時完全不保存此欄位，繼續驗證原本格式的前版讀寫。
